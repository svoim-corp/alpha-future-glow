# AGENTS.md — backend

Правила написания кода серверной части. Дополняет корневой `../AGENTS.md`; запуск, переменные окружения,
структура каталогов и зависимости — в `README.md`.

Главный принцип: **код должен выглядеть так, будто его написал один аккуратный человек**. Прежде чем писать новое,
открой реализованную зону (`internal/identity`, `internal/company`) и пакеты `internal/platform/*` и повторяй их приёмы.

## Команды

```bash
make build    # go build ./...
make vet      # go vet ./...
make test     # go test ./...
make fmt      # gofmt -l . — вывод должен быть пустым
make swagger  # после изменения swag-аннотаций, docs/ коммитится
```

Перед завершением задачи `make fmt vet build test` должны проходить без ошибок.

## Архитектура

Модульный монолит: `internal/<zone>` — одна доменная зона, `internal/platform/*` — инфраструктура без бизнес-логики,
`internal/shared` — контракты между зонами. Сборка всего — только в `cmd/api/main.go`.

Направление зависимостей строго одно:

```
cmd/api  →  internal/<zone>  →  internal/shared, internal/platform/*
```

- Зона **не импортирует** другую зону. Нужны данные или действие другой зоны — интерфейс в `shared/<зона-поставщик>.go`,
  реализация в зоне-владельце (аксессор в её `ports.go`), поле в `Ports` зоны-потребителя, подстановка через `Wire`
  в `cmd/api/main.go`. Интерфейс описывает потребность потребителя,
  а не всё, что умеет владелец: держи его маленьким (1–3 метода).
- `platform` и `shared` не импортируют зоны. `shared` — только типы, константы и интерфейсы, без логики и без БД.
- Зона владеет своей схемой БД. **Никаких SQL-запросов к чужой схеме**, никаких JOIN между схемами.
- Статус заявки меняет только Origination (`shared.Applications.Transition`).
- Внешние сервисы — только из зоны Integrations, только HTTP к контейнеру моков (`MOCKS_BASE_URL`).
- Реакция одной зоны на событие другой — через `events.Bus`, публикация **после** коммита транзакции.

### Слои внутри зоны

| Файл | Что там | Чего там нет |
|---|---|---|
| `module.go` | `Module`, `Ports`, `New(deps)`, `Migrate`, `Wire`, `Register` | логики запросов |
| `ports.go` | аксессоры реализаций `shared`-интерфейсов для других зон (`Products()`, `Applications()`) | — |
| `handlers.go` | разбор запроса, `auth.UserFrom`, вызов сервиса/стора, маппинг в DTO, swag-аннотации | бизнес-правил, SQL |
| `service.go` | бизнес-правила, транзакции, вызовы других зон через `shared`, публикация событий | `gin`, `http`, DTO |
| `store.go` | SQL-запросы и `*Row`-структуры с тегами `db` | бизнес-решений |
| `dto.go` | структуры запросов/ответов с тегами `json`/`binding`/`example` (если их много) | — |
| `migrations/` | `NNNN_name.sql` для goose | — |

- Для простого чтения хендлер может звать стор напрямую (как `identity`). Как только появляются правила,
  несколько шагов, транзакция, событие или вызов другой зоны — выноси в `service.go`.
- Сервис не знает про HTTP: принимает `context.Context` и доменные значения, возвращает доменные значения и `error`.
  Прикладные ошибки он может возвращать как `httpx.NotFound(...)`, `httpx.BusinessRule(...)` и т.п. — это наш
  единый контракт ошибок.
- Большая зона растёт файлами по подзонам (`handlers_stage1.go`, `service_submit.go`), а не подпакетами.
  Подпакет — только для действительно отдельной сущности с собственным API.

## Стиль Go

- `gofmt` обязателен. Импорты тремя группами: стандартная библиотека, сторонние, `github.com/svoim-corp/...`.
- Имена — по Effective Go: короткие для локальных (`u`, `r`, `err`), говорящие для экспортируемых.
  Без `Get` в геттерах, без заикания (`company.Company`, а не `company.CompanyStruct`), аббревиатуры
  целиком в одном регистре (`ID`, `INN`, `URL`, `HTTP`).
- Экспортируй только то, что нужно снаружи пакета. Хендлеры, DTO, `*Row` — неэкспортируемые.
- Функция делает одно дело. Ранний возврат вместо вложенных `if/else`; «счастливый путь» — без отступа.
- Никаких глобальных изменяемых переменных и `init()` с побочными эффектами (кроме `//go:embed` и регистрации
  валидатора в `httpx`). Зависимости передаются через конструктор `New` и поля структуры.
- Магические числа и строки — в именованные константы рядом с местом использования.
- Обобщения (`generics`) — только когда убирают реальное дублирование (как `httpx.Page[T]`), не «на будущее».
- Не создавай интерфейс ради одной реализации внутри пакета. Интерфейс объявляет потребитель.
- Не пиши код «на вырост»: никаких неиспользуемых параметров, флагов, абстрактных фабрик и `utils`/`helpers`/`common`
  пакетов. Нужна общая утилита для нескольких зон — она идёт в подходящий `platform/*`.

### Комментарии

- На русском. Пакет — `// Package x — ...` с указанием зоны и владельца (см. существующие).
- Комментарий объясняет **почему**, а не что: неочевидное правило, ссылку на раздел `API_SPEC.md`, договорённость
  (`// (nil, nil) — компании нет`). Пересказ кода не нужен.
- Экспортируемые типы и функции — с doc-комментарием, начинающимся с имени.

## Ошибки

- Ошибку **либо обрабатываешь, либо возвращаешь** — не оба сразу (не логируй и не возвращай одновременно).
  Логирует только `httpx.Fail` на границе.
- Игнорировать ошибку можно только явно `_ =` и только там, где это осмысленно (rollback, close на пути ошибки).
- Добавляй контекст при пробросе: `fmt.Errorf("load application %s: %w", id, err)`. Сравнение — `errors.Is/As`,
  не по строке.
- В хендлере любая ошибка уходит через `httpx.Fail(c, err)` и сразу `return`. Своих `c.JSON(4xx, ...)` не писать.
- Ответ клиенту — только прикладные ошибки из `httpx` (`Validation`, `NotFound`, `Forbidden`, `InvalidTransition`,
  `VersionConflict`, `BusinessRule`, `Upstream`). Новый код ошибки — сначала в `API_SPEC.md`, раздел 3, потом
  константа и конструктор в `httpx/errors.go`.
- Текст ошибки для пользователя — на русском и понятен клиенту. Внутренние детали (SQL, стектрейс, ответ мока)
  наружу не уходят.
- «Не найдено» в сторе — `(nil, nil)`, как в существующем коде; решение «это 404» принимает сервис/хендлер.
- `panic` — только для ошибок программиста при старте. В обработке запросов — никогда.

## HTTP и контракт API

- Каждый эндпоинт есть в `API_SPEC.md`. Нет в спецификации — сначала добавь туда (пометка «Доп.»), потом код.
- Тело запроса — `httpx.Bind(c, &req)` со структурой и тегами `binding`; ручной валидации полей, которую можно
  выразить тегом, быть не должно. Бизнес-валидация (зависит от продукта, статуса, данных в БД) — в сервисе.
- Ответ — `httpx.JSON`; списки — `httpx.NewPage` + `httpx.ParsePage` (items никогда не `null`).
- Наружу отдаются только DTO, никогда `*Row` из стора: схема БД и контракт API меняются независимо.
- JSON-поля — `camelCase`; деньги — целые рубли `int64`; ставки — `float64` в процентах годовых; сроки — месяцы `int`;
  даты — `time.Time` (сериализуется в ISO 8601). Никаких `float` для денег.
- Изменение заявки — с `httpx.IfMatch(c)` и проверкой версии (`httpx.VersionConflict()` при несовпадении).
- Команды с побочным эффектом — с `m.deps.Idem.Middleware()` на роуте.
- **Проверка доступа обязательна в каждом хендлере**: клиент видит и меняет только данные своей компании
  (`auth.UserFrom(c).CompanyID`), ролевой доступ к `/bank/*` уже обеспечен группой `r.Bank`. Чужой объект —
  `httpx.Forbidden(...)` (`API_SPEC.md`, раздел 3).
- Каждому хендлеру — swag-аннотации (как в `identity/handlers.go`), затем `make swagger`.

## База данных

- Только `sqlx` и явный SQL с плейсхолдерами `$1, $2`. **Никакой конкатенации пользовательских данных в SQL.**
  Конкатенация допустима только для констант (список колонок `userCols`).
- Таблицы всегда с именем схемы: `identity.users`. Колонки в `SELECT` — перечисляются явно, без `*`.
- Все запросы — с `ctx` (`GetContext`, `SelectContext`, `ExecContext`), контекст берётся из `c.Request.Context()`.
- Несколько изменений, которые должны пройти вместе, — в `db.WithTx`. Методы стора, которые используются внутри
  транзакции, принимают `sqlx.ExtContext`, чтобы работать и с `*sqlx.DB`, и с `*sqlx.Tx`.
- Внутри транзакции — никаких HTTP-вызовов и публикации событий. Сначала коммит, потом события.
- Конкурентные изменения одной записи — через версию (`UPDATE ... WHERE id = $1 AND version = $2`, проверка
  `RowsAffected`) или `SELECT ... FOR UPDATE`, а не через проверку в Go между двумя запросами.
- Списки — всегда с `LIMIT/OFFSET` и стабильной сортировкой (`ORDER BY created_at DESC, id`).
- Избегай N+1: одно чтение списка — один-два запроса, а не запрос на каждый элемент.
- Миграции — goose, `-- +goose Up` и `-- +goose Down`, номер по порядку. **Применённую миграцию не меняй** —
  пиши новую. Ограничения целостности (`NOT NULL`, `UNIQUE`, `REFERENCES`, `CHECK`) — в схеме, а не только в коде.
  Внешние ключи — только внутри своей схемы.
- `jsonb` — через `db.JSON[T]`. Nullable-колонки — указатели (`*string`) или `sql.Null*`.
- Seed-данные — отдельной миграцией с понятными id (`u-1`, `c-1`).

## Контекст, конкурентность, время

- `context.Context` — первый параметр каждой функции, которая ходит в БД, сеть или другую зону. В структурах не хранить.
- HTTP-клиенты — с таймаутом, запросы — через `NewRequestWithContext`, тело ответа закрывается.
- Горутину запускай только если понятно, кто и как её остановит и куда уйдёт её ошибка.
  Общие данные — под `sync.Mutex`; тесты запускаются с `-race`, когда есть конкурентный код.
- Время — в UTC. Если логика зависит от «сейчас» (сроки, просрочка), передавай время/часы параметром,
  чтобы это можно было протестировать.

## Логирование

- Только `log/slog`, структурно: `slog.Error("msg", "key", value)`. Никаких `fmt.Println` и `log.Printf`.
- Не логируй пароли, токены сессий, полные персональные данные и тела запросов с ними.
- Сообщения логов — короткие, на английском, в нижнем регистре; детали — в атрибутах.

## Тесты

- Табличные тесты (`tests := []struct{...}` + `t.Run`) для бизнес-правил: расчёт лимитов, ставок, переходы статусов,
  проверка полноты. Это самое ценное, покрывай в первую очередь.
- Хендлеры — через `httptest` и `gin.TestMode`, как в `platform/httpx/httpx_test.go`.
- Зависимости из других зон в тестах подменяются фейковой реализацией `shared`-интерфейса, без моков-генераторов.
- Тест проверяет поведение (код ответа, тело, состояние), а не внутренние детали реализации.
- Новая логика без теста — незаконченная задача. Исправленный баг — с тестом, который его воспроизводит.

## Безопасность

- Пароли — только `bcrypt`. Токены и секреты — из `crypto/rand`.
- Секреты и строки подключения — из переменных окружения через `platform/config`, не в коде.
- Данные из запроса не доверенные: проверяй принадлежность объекта пользователю, границы чисел, допустимые
  значения перечислений.

## Чек-лист перед завершением

1. Контракт совпадает с `API_SPEC.md` (или спецификация обновлена в том же изменении).
2. Зона не импортирует другие зоны и не читает чужую схему.
3. Доступ проверен: клиент не дотянется до чужой компании.
4. Ошибки идут через `httpx.Fail`, тексты для пользователя — на русском.
5. Новые правила покрыты тестами; `make fmt vet build test` проходят.
6. Swag-аннотации добавлены, `make swagger` выполнен, `docs/` обновлён.
7. В диффе нет несвязанных правок, отладочного вывода и закомментированного кода.
