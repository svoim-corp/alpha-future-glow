# Настраиваемая главная

Обновлено 22.10.2026. Клиентский каталог расширен с восьми до шестнадцати типов виджетов по [дизайн-концепции](../frontend/docs/designs/HOME_WIDGETS.md). Начальная раскладка по-прежнему содержит восемь виджетов; новые добавляются пользователем. Существующие сохранённые раскладки автоматически не меняются. Клиент подключён к серверному хранению через RTK Query: `GET` и `PUT /api/v1/me/dashboard`. Действующий контракт — [dashboard.md](dashboard.md). Ограничения источников и возможные улучшения перечислены ниже.

## Поведение

Главная содержит независимые виджеты. Первые восемь: «Мои заявки», «Мой кредит», «Ближайший платёж», «Основной долг», «Быстрые действия», «Календарь событий», «Мои планы», «Конкретная заявка». Дополнительно доступны «Все кредиты», «Платежи на период», «Предложения банка», «Черновики», «План и финансирование», «Уведомления», «Обращения в банк», «Подобрать финансирование». Оформление каждого типа фиксировано. Можно добавить несколько экземпляров, привязав их к разным договорам, заявкам и планам.

Настройка главной создаёт черновик. Перемещение, смена размера, удаление, добавление и сброс изменяют только его. «Сохранить» применяет всю конфигурацию атомарно; при неудаче черновик остаётся доступен. «Отмена» возвращает сохранённую раскладку. Уход со страницы с открытым черновиком требует явного отказа от настройки; перезагрузка вызывает стандартное предупреждение браузера.

Удаление виджета не удаляет бизнес-объект. Выбранные договоры и заявки сохраняются по идентификаторам, не подменяются первым доступным объектом. Если источник не выбран, предлагается выбрать его; если недоступен — отображается ошибка, настройка не исчезает.

Запросы по заявкам, требующим действия, отображаются вне настраиваемой сетки. Скрытие виджета не скрывает этот блок. Ошибка проверки действий явно сообщается и имеет повтор запроса.

## Сетка

Компьютер: 12 колонок, ряд 64 px, промежуток 16 px. Позиция — `x, y` от нуля, размер — `w, h`. В режиме настройки у каждой карточки есть четыре ручки размера — по центру сторон. Они работают мышью и касанием, привязываются к разрешённым размерам и удерживают противоположную сторону на месте. Сторона с фиксированным размером недоступна. Стрелки на ручке меняют размер с клавиатуры, Escape или отмена указателя отменяют текущий жест. Предпросмотр перестраивает соседей; отпускание применяет размер к черновику, сохранение на сервер — общей кнопкой «Сохранить». На планшете и телефоне размер по-прежнему задаётся в настройках, без изменения правил адаптивной проекции. Браузер и тесты для доработки не запускались по указанию пользователя.

Перетаскивание работает за отдельную ручку; место назначения подсвечивается. Новая позиция закрепляется, пересекающиеся элементы детерминированно занимают свободные клетки. Пересечения и выход за 12 колонок запрещены.

Планшет: шесть колонок с проекцией широких карточек на шесть, компактных — на три. Сохраняется порядок чтения без плотной упаковки, которая могла бы поменять визуальный порядок. Перетаскивание меняет порядок. Телефон: одна колонка с естественной высотой содержимого. В панели виджета оставлены ручка переноса, настройки и удаление. Порядок меняется в настройках через поле «Положение на главной», а с клавиатуры также клавишами ↑/↓ на ручке. Адаптация не записывает новую десктопную раскладку.

Допустимые размеры и названия перечислены в `entities/dashboard/model/definitions.ts`. Все конфигурации проверяются схемой: версия, типы, настройки, диапазоны координат, разрешённые размеры, уникальные ID и отсутствие пересечений. Лимит — 30 экземпляров. Контент не масштабируется шрифтом: у увеличенных размеров появляется дополнительная информация; длинные списки ограничены превью и ведут к полным разделам. Внутренней прокрутки у виджетов нет. Представления адаптируются к фактической ширине и высоте карточки: второстепенный текст сокращается, основные суммы и переходы сохраняются. Списки используют общий `WidgetPreview` с `ResizeObserver`: выводятся только целые строки, помещающиеся после заголовка, пояснений и ссылки; невидимые записи не рендерятся и не попадают в Tab-порядок. На телефоне карточки растут по содержимому, списки ограничены тремя записями. Календарь распределяет доступную высоту между всеми неделями. Компактный кредит объединяет подпись погашения со ссылкой на детали.

## Источники данных

- Заявки: существующий `GET /applications?mine=true&page=N&size=100`. Переиспользуемый запрос сущности `getAllMyApplications` проходит страницы, проверяет неизменность total и количество уникальных ID. Ошибка любой страницы или неполнота не выдаётся за полный результат. Список предложений использует этот же запрос и отдельно загружает условия банка. Ограничитель на 1000 страниц завершает запрос явной ошибкой, не частичным успехом.
- Выбранная заявка: `GET /applications/{id}`; переход учитывает статус черновика.
- Выбранный кредит: `GET /loans/{id}`; статус, условия, остаток, график. Прогресс — доля погашенного основного долга, не количество оплаченных месяцев.
- Общий ближайший платёж: `GET /loans/summary`; это сумма всех платежей ближайшей даты, без подписи конкретного договора. Отдельный договор использует только свой график.
- Основной долг: серверный `GET /loans/summary.totalPrincipalBalance` по всей компании. Выбор и список договоров используют все страницы `GET /loans/page`.
- Планы: `GET /plans?state=ACTIVE`; ближайшие — датированные, у которых ещё не закончился период по московскому дню Planner; идеи — без даты.
- Календарь: `GET /loans/schedule?from&to` и активные планы. Источники можно включить вместе или по отдельности. Используются даты без переноса между часовыми поясами. Для платежей текущий месяц и сегодняшний день основаны на UTC, как в Servicing; планы привязаны к сохранённым календарным датам.

Календари имеют выбор месяца/года и список событий дня в модальном окне. Запрос нового периода использует `currentData`: прежний месяц не показывается под новым заголовком. События одного кредита с одинаковыми датой и статусом объединяются по сумме с сохранением числа платежей: API периода не возвращает ID строки. Разные статусы не смешиваются. Ссылки на договор передают его ID в `/credits?loan=...`; страница кредитов выбирает этот договор и соответствующую вкладку, включая закрытые. Изменение параметров URL сбрасывает прежний выбор страницы, чтобы новый переход не открывал старый договор. Ссылки планов ведут в планер без автоматического открытия отдельного плана.

Серверные данные остаются в RTK Query. Повторные виджеты делят кеш одинаковых запросов. Каждый виджет независимо обрабатывает загрузку, ошибку и пустоту; ошибки не превращаются в нулевые суммы. Банковских данных в настройке нет.

## Архитектура FSD

| Уровень | Ответственность |
|---|---|
| `shared/lib/grid` | Чистые алгоритмы пересечений, размещения, порядка и адаптивной проекции; без доменов банка |
| `shared/ui/TileGrid` | Универсальное отображение сетки, ручка переноса, доступные команды, подсветка места назначения |
| `entities/dashboard` | Формат конфигурации, discriminated union настроек, реестр допустимых типов/размеров, Zod-валидация, начальная конфигурация, RTK Query API чтения и сохранения |
| `features/customize-dashboard` | Redux-слайс черновика и исходного снимка, хук редактора поверх RTK Query, каталог и диалог настройки экземпляра |
| `widgets/home-dashboard` | Композиция главной и шестнадцать представлений на существующих API сущностей; связывание UI с командами |
| `app/model` | Регистрация редьюсера редактора и общего API; сетевые адаптеры через thunk extraArgument не внедряются |

Нет импортов между слайсами одного слоя, сырых сетевых запросов, финансовых моков или новых зависимостей. Типы реальных API остаются в своих сущностях. Алгоритм сетки не знает о кредитах и заявках. Registry не содержит JSX и сетевых хуков; switch рендеринга — исчерпывающий по discriminated union, без строкового выбора произвольного компонента.

## Серверное хранение

`entities/dashboard/api/dashboardApi.ts` читает и сохраняет документ `revision`, `updatedAt`, `config`. `schemaVersion` относится к формату конфигурации, `revision` — к версии записи. В RTK Query ключ кеша содержит пользователя и компанию; сервер получает их из сессии, а не из тела запроса. Финансовые значения, названия компаний и тексты заявок в config не входят.

- `GET /me/dashboard`: `200` — сохранённая настройка; `204` — исходные восемь виджетов. Сохранённый пустой массив остаётся пустым. Ответы проверяются Zod целиком: неизвестный тип, неподдерживаемый формат или повреждённый документ блокируют редактирование, а не заменяются исходной настройкой.
- `PUT /me/dashboard`: в теле только config. Первое сохранение — `If-None-Match: *`, дальнейшее — `If-Match: "<revision>"`. Версия фиксируется при начале редактирования, фоновое чтение не меняет её у открытого черновика.
- `Idempotency-Key` — UUID одной попытки. Неизменённые тело и исходная версия при повторе сохраняют ключ; изменение любого из них создаёт новый. После потери ответа повтор получает первоначальный результат без повторной записи.
- Успешный PUT инвалидирует тег Dashboard в области пользователя и компании, в том числе после ухода со страницы. На открытой главной обновляется кеш чтения, редактор закрывается, появляется «Главная сохранена в вашем профиле». Затем запись перечитывается: идемпотентный повтор мог вернуть результат, после которого настройку уже меняли снова.
- При `412` и других ошибках черновик остаётся. «Отменить изменения и загрузить сохранённую» явно отбрасывает его и перечитывает сервер; автоматического перезаписывания чужих изменений нет. Ошибки полей сервера выводятся вместе с сообщением.

Серверный документ остаётся в RTK Query. Redux редактора хранит только исходный снимок config и revision на время настройки, черновик и состояния UI. Они сбрасываются вместе с кешем сессии; завершение сохранения применяется только к совпадающему requestId. При открытии главной, возврате фокуса и восстановлении сети настройка перечитывается. Во время редактирования обновления по фокусу/сети отключены, версия всё равно защищена серверным предусловием.

### Прежние настройки устройства

Локальная запись `credit-dashboard:v1:<userId>:<companyId>` больше не используется как основное хранилище и не изменяется. Если сервер ответил `204` и на устройстве есть прежняя настройка, доступна кнопка «Перенести настройку с устройства». Она загружает конфигурацию только в черновик; отправка — отдельной кнопкой «Сохранить» с `If-None-Match: *`. Запись, появившаяся на другом устройстве, даст конфликт. При существующей серверной настройке перенос не предлагается, автоматической миграции нет. Ключ HTML-прототипа не читается.

## Границы и проверка

Изменён только клиент и документация. Сервер, клиентские моки и инфраструктура проверок не менялись. По указанию пользователя тесты не добавлялись; браузер, тесты, сборка, линтер и проверка типов не запускались. Визуальная и сквозная проверка с пользовательским сервером остаётся невыполненной.

## Дополнительные восемь типов

| Тип / код | Настройки | Источник и поведение |
|---|---|---|
| Все кредиты / `loans` | `status: ACTIVE / CLOSED` | Все страницы `GET /loans/page`, превью до 3–4 договоров и переход к выбранному. Ошибка страницы или неподтверждённая полнота — ошибка запроса, частичный список не публикуется |
| Платежи на период / `payments` | `days: 7 / 30`, `loanId: null / ID` | `GET /loans/schedule` за скользящие 7/30 дней от сегодня по UTC включительно. Только `PLANNED`; группировка по датам, сумма периода, полосы величины платежей. Узкий размер — компактный список. Привязанный кредит дополнительно читается по ID для проверки доступа |
| Предложения банка / `offers` | `filter: current / all` | Существующий `getPendingOffers`: все страницы заявок, затем условия каждой. Показаны только `offered` суммы/ставки/сроки. `current` исключает истёкшие непринятые предложения; `SIGNING` остаются. Ошибки отдельных условий явно показаны и имеют повтор. Переход к подписанию либо заявке; полный список — вкладка «Одобренные» |
| Черновики / `drafts` | `{}` | Полный список заявок, `status=DRAFT`, последние изменённые первыми. Кнопка продолжения ведёт в существующий мастер |
| План и финансирование / `planFunding` | `planId: null / ID` | `GET /plans`, выбранный план и его серверное поле `recommendation`. Клиент не выдумывает рекомендацию. Отсутствующий вариант отличается от ошибки запроса. Переходы в планер и каталог, без автоматической подачи заявки или обещания одобрения |
| Уведомления / `notifications` | `filter: unread / all` | `GET /notifications?unread=true` либо существующий общий список. До 50 последних записей, общий `unreadCount` берётся с сервера; обновление раз в минуту. При открытии непрочитанного вызывается существующий POST `/notifications/{id}/read`. При ошибке отметки доступен отдельный переход без ложного успешного статуса |
| Обращения в банк / `tickets` | `filter: active / answered / all` | `GET /support/tickets`, последние 100. `active` — OPEN и ANSWERED, `answered` — ANSWERED. Карточка открывает модальное окно с текстом обращения и ответом; переход в поддержку сохраняет контекст заявки |
| Подобрать финансирование / `funding` | `{}` | `GET /products`, реальные названия и диапазоны ставок нескольких продуктов. Акцентный блок и переход в каталог; нет вымышленных персональных лимитов |

Дополнительные типы вписываются в формат `schemaVersion: 1` без изменения структуры существующих записей. Ранее сохранённые конфигурации из восьми типов остаются валидными. Старый клиент, который ещё не знает новых типов, должен сохранить документ без перезаписи и предложить обновить приложение, а не молча удалять неизвестные виджеты.

Ограничения API отражены в интерфейсе: уведомления — последние 50, обращения — последние 100, планы — до 200. Фильтр обращений применяется к полученной выборке; непрочитанные уведомления фильтруются на сервере. Это превью событий, а не полная история. У выбранного плана за границей списка нельзя гарантировать загрузку: ID сохраняется, показывается отсутствие в полученном списке, предлагается выбрать другой план. Кредиты загружаются всеми страницами `GET /loans/page` по 100 записей; выбор договора и `/credits` используют тот же запрос, поэтому переход из виджета доступен и за пределами первой страницы. Защитный предел обхода — 1000 страниц; при его достижении возвращается ошибка без усечённого результата. Сводный основной долг виджета берётся из `GET /loans/summary.totalPrincipalBalance`, без суммирования списка. Сумма ближайшей строки выбранного кредита определяется общей функцией сущности `paymentAmounts`: серверный `remainingTotal` приоритетен, для прежнего формата остаток определяется по оплаченным суммам и статусу. Эта же функция используется страницей кредита.

Для переходов уведомлений допускаются только внутренние адреса клиентских разделов; внешние URL не открываются. Разметка текста из API не интерпретируется как HTML. Отметка прочтения инвалидирует общий кеш уведомлений, включая колокольчик. При ошибке отметки доступен просмотр полного текста или отдельный переход к событию, без ложного успешного статуса.

Новые виджеты используют существующие endpoints; новые серверные API для их текущих превью не требуются. Синхронизация раскладки подключена к серверу. Возможные доработки источников перечислены ниже; они не считаются реализованными.

## Возможные улучшения источников

Эти задачи не блокируют текущие превью; новых маршрутов клиент для них не придумывает.

- Уведомления: пагинация или курсор полной истории, стабильная сортировка и признак продолжения. Общий `unreadCount` должен оставаться числом непрочитанных пользователя, а не размером страницы.
- Обращения: пагинация и серверные фильтры OPEN/ANSWERED/CLOSED. Фильтр последних 100 записей не гарантирует нахождения старых открытых обращений.
- Планы: GET по ID с проверкой компании и одинаковым 404 для отсутствующего/чужого уже реализован для общего поиска. Для выбора в каталоге виджетов остаётся полезна пагинация списка; виджет финансирования пока использует старый список до 200.
- Предложения банка: возможный агрегированный API для уменьшения числа запросов; текущая реализация использует общий полный список заявок сущности и читает условия отдельно.
