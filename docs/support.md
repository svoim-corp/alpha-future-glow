# Support — поддержка

## Локальный ассистент

### Расширение действий, 22.10.2026

Уточнение интерфейса: `GET /conversations` дополнительно возвращает `title` — первые
80 символов первого вопроса либо «Новый диалог». Клиент группирует диалоги по
календарным дням в часовом поясе браузера; внутри дня показывает названия переписок.
Enter отправляет вопрос, Shift+Enter вставляет строку; во время обработки повтор
заблокирован. Пустое сообщение не отправляется.

В карточке заявки добавлено `canDelete`: только для текущего статуса DRAFT.
Для обновления истории Origination предоставляет пакетное чтение `AssistantApplications.Find`
по компании и набору ID; Support не делает отдельный запрос для каждой карточки.
Кнопка использует существующий `DELETE /api/v1/applications/:id` и подтверждение.
Origination закрывает черновик, повторно проверяя владельца и статус. При чтении
истории Support актуализирует карточки заявок через порт Origination и заменяет
удалённый черновик отметкой; старые карточки не предлагают открыть его повторно.

Имя и должность пользователя поступают из доверенного контекста текущей сессии,
сохраняемого с его сообщением (этот контекст не возвращается API сообщений и не
индексируется). Карточка компании дополнена `viewerName?`, `viewerPosition?`.
Вопросы о своём имени, должности и названии компании читают данные кабинета,
а не справочную базу. Пользователь не задаёт ID компании или другого пользователя.

Согласованное расширение: управление кабинетом обычным текстом. Новые карточки
`navigation {section,label,href}`, `plan {id,title,goal,budgetRub,dateMode,startDate?,endDate?,state,updatedAt}`,
`loan {id,productName,amount,balance,rate,term,status}`, `company {name,inn,regAddress,actualAddress,monthlyIncome}`,
`ticket {id,subject,text,status,reply?}` добавляются в прежний `blocks` без новых HTTP-маршрутов.
Ссылки строит сервер из фиксированных маршрутов; внешних адресов от модели нет.
Переход выполняется по кнопке, без неожиданного ухода из переписки.

Новые функции: `navigate`, `plans`, `propose_plan`, `loans`, `company`, `tickets`.
`propose_plan` готовит создание или изменение плана (название, цель, бюджет, заметка,
даты, ACTIVE/PAUSED/DONE/ARCHIVED). Action `kind=plan` содержит `planChange` и
полную `planPreview`. Изменение требует кнопки подтверждения; слово «да» ничего
не сохраняет. Даты — YYYY-MM-DD, текущая дата передаётся модели сервером.
Планер повторно проверяет владельца, аргументы и `expectedUpdatedAt`; устаревшее
предложение отклоняется. Запись команды и результат сохраняются атомарно в схеме
Planner; повтор, включая сбой до записи результата Support, не повторяет изменение.
Удаление без восстановления, денежные команды, подписание и согласия остаются
на штатных страницах, на которые ассистент даёт кнопку перехода.

Разбор запроса возвращает намерения и типизированные параметры в одном JSON.
Сокращения «150к», «1,5 млн», «на год» приводятся к рублям и месяцам.
Финансовые параметры дополнительно сохраняются с ответом на сервере (в API и RAG
этот контекст не попадает). Связанное уточнение использует их, а новая цель
не получает сумму и срок прежней задачи автоматически. Неизвестные поля в схеме
разбора явно nullable; вся схема передаётся модели вместе с инструкцией.
Уже известные параметры сохраняются в контексте уточнения. Для неоднозначной
покупки личного назначения уточняется только использование для бизнеса;
потребительские кредиты здесь не предлагаются. Если продукт не выбран, бот
показывает подходящие варианты, а не выбирает его молча для создания черновика.
Данные компании, кредитов и планов приходят через shared-порты владельцев модулей;
обращения — только текущего пользователя. Текст рядом с карточками формирует сервер.

Согласованный контракт: только CLIENT; компания и пользователь определяются сессией.
История принадлежит конкретному пользователю. FAQ и обращения работают без ИИ.

Все пути ниже имеют префикс `/api/v1/support`:

| Метод | Путь | Запрос / ответ |
|---|---|---|
| GET | `/conversations` | последние 100 диалогов: `{id, applicationId, createdAt}`[] |
| POST | `/conversations` | `{applicationId?}` → 201, диалог |
| GET | `/conversations/:id/messages` | последние 100 сообщений, по времени: `{id, role, status, text, sources, blocks, createdAt}`[] |
| POST | `/conversations/:id/messages` | `{text}` (1–4000 символов), `Idempotency-Key` → 202, сообщение пользователя и сохранённое PENDING-сообщение ассистента |
| POST | `/conversations/:id/actions/:actionId/confirm` | `Idempotency-Key` → 200, карточка результата; повтор возвращает тот же результат |

Списки — JSON-массивы, как существующие списки поддержки. `role`: user/assistant;
`status`: PENDING/COMPLETED/FAILED. Опрос сообщений раз в секунду только пока есть PENDING.
Один незавершённый вопрос на диалог. Повтор вопроса после ошибки — новое сообщение.
После перезапуска незавершённые сообщения получают FAILED. Обработка — до 120 секунд,
не более трёх раундов функций. Ошибка не содержит внутренних ответов Ollama/SQL.

`sources`: `{id,title,href,excerpt}`[] — реальные найденные материалы с текстом фрагмента и локальными ссылками.
`blocks`: дискриминированные карточки `{kind,title,product?,calculation?,application?,payment?,actionId?,action?,resultId?}`.
Виды: product, calculation, application, payment, action, result. Числа и карточки
формирует сервер по результатам доменных функций, не из свободного текста модели.
Параметры action: `{kind: draft|ticket, draft?: {productCode,amount,term,goal}, productName?, goalLabel?, subject?, text?}`.
Предложение хранится на сервере и связано с диалогом; клиент передаёт только actionId.
Повтор подтверждения использует сохранённый результат. Для восстановления после сбоя
доменная команда получает стабильный идентификатор, исключающий дубликат даже при
одновременных подтверждениях. HTTP-вызовов внутри транзакции нет.
Черновик использует тот же доменный сервис и проверки полномочий.
Никакой отправки заявки, согласий и подписания через ассистента нет.

Межзонные данные поступают через shared-интерфейсы Catalog, Origination, Servicing.
Пользовательский текст и найденные фрагменты считаются данными, а не инструкциями.
Модель не получает SQL, доступ к файлам или произвольным URL. Условия кредита берутся
из каталога при вызове; расчёт выполняет калькулятор Catalog.

Знания: подготовленные Markdown в `backend/internal/support/knowledge`; отдельная команда
`go run ./cmd/support-index`. BGE-M3 dense (1024), полнотекстовый поиск PostgreSQL,
объединение reciprocal rank fusion, максимум пять источников. Обновление индекса атомарное;
хеши и версия сохраняются, удалённые фрагменты удаляются. Нет личных данных и исходников.
Встроенные FAQ включаются при индексации. Все конфигурации запуска и ограничения — `deploy/SUPPORT_AI.md`.

Подготовка моделей проверяет manifest SHA256 из `deploy/models.sha256`. Если оба
manifest уже совпадают, скачивание не выполняется. При смене весов нужно обновить
этот файл вместе с именами моделей и повторно построить индекс.

Перед ответом Qwen выбирает намерения в структурированном JSON: справка либо
разрешённые функции (максимум три намерения). Для заявок и платежей сервер сам
выполняет свежие чтения, даже если сведения встречались в истории. Для подбора,
расчёта и предложений модель извлекает параметры через ограниченные tool calls.
Текст рядом с карточками данных и предложениями формирует сервер. Модель не может
назвать предложение созданным объектом или заменить актуальную карточку пересказом
старого сообщения. При нехватке параметров возвращается просьба уточнить их.

Классификация относится только к текущему сообщению. История передаётся как пассивный
контекст для уточнений, а не как повторные команды. Отдельное приветствие получает
краткий ответ о возможностях кабинета без загрузки личных данных и поиска справки.

После обновления обслуживания кредита карточка ближайшего платежа показывает остаток
к оплате с учётом частичных погашений. Просрочка не входит в список предстоящих платежей.

Зона Support (`backend/internal/support`, разработчик A): частые вопросы и обращения клиента. Схема БД — `support`,
вопросы — seed-миграция `0002_seed.sql`.

Ответы на обращения пока никто не пишет: кто отвечает (сотрудник банка или только частые вопросы) — открытый вопрос
в `backend/TASKS.md`. Поэтому обращение остаётся в статусе `OPEN`, `reply` — `null`, уведомление `TICKET_REPLY`
не отправляется.

## API

### `GET /support/faq?step=APPLICATION`

Реализовано. Открыто без входа. Частые вопросы по шагу пути клиента: `PRODUCT`, `APPLICATION`, `DOCUMENTS`,
`STATUS`, `DECISION`. Без `step` — по всем шагам. Неизвестный шаг — `400 VALIDATION_ERROR`.

```json
[
  { "id": "f-4", "step": "APPLICATION", "question": "Нужно ли загружать документы или выписки?", "answer": "Нет. Данные о компании, руководителе, учредителях и оборотах банк берёт из ваших счетов и государственных реестров." }
]
```

Шаг `DOCUMENTS` — про документы к подписанию, которые банк формирует сам: загрузки документов в кабинете нет.

### `POST /support/tickets`

Реализовано. Новое обращение клиента (пользователь с компанией; сотрудник банка — `403`). Со страницы заявки фронт
передаёт `applicationId`; это может быть только заявка своей компании, иначе — `400 VALIDATION_ERROR` по полю
`applicationId` (о чужой заявке через поддержку ничего не узнать).

Запрос:
```json
{ "subject": "Устаревший фактический адрес", "text": "В заявке старый адрес склада, мы переехали", "applicationId": "a-1031" }
```
Ответ `201`:
```json
{ "id": "t-12", "status": "OPEN", "createdAt": "2026-10-20T11:00:00Z" }
```

`subject` — до 200 символов, `text` — до 4000. `POST /admin/seed/reset` удаляет обращения, частые вопросы остаются.

### `GET /support/tickets`

Реализовано. Обращения текущего пользователя (последние 100), недавно изменённые первыми. Обращения коллег из той же
компании не показываются: это переписка конкретного человека.

```json
[
  { "id": "t-12", "subject": "Устаревший фактический адрес", "text": "В заявке старый адрес склада, мы переехали", "status": "OPEN", "reply": null, "applicationId": "a-1031", "updatedAt": "2026-10-20T11:00:00Z" }
]
```
