# Support — поддержка

## Локальный ассистент

Согласованный контракт: только CLIENT; компания и пользователь определяются сессией.
История принадлежит конкретному пользователю. FAQ и обращения работают без ИИ.

Все пути ниже имеют префикс `/api/v1/support`:

| Метод | Путь | Запрос / ответ |
|---|---|---|
| GET | `/conversations` | последние 100 диалогов: `{id, applicationId, createdAt}`[] |
| POST | `/conversations` | `{applicationId?}` → 201, диалог |
| GET | `/conversations/:id/messages` | последние 100 сообщений, по времени: `{id, role, status, text, sources, blocks, createdAt}`[] |
| POST | `/conversations/:id/messages` | `{text}` (1–4000 символов), `Idempotency-Key` → 202, сообщение пользователя и сохранённое PENDING-сообщение ассистента |
| POST | `/conversations/:id/actions/:actionId/confirm` | `Idempotency-Key` → 200, карточка результата; повтор возвращает тот же результат |

Списки — JSON-массивы, как существующие списки поддержки. `role`: user/assistant;
`status`: PENDING/COMPLETED/FAILED. Опрос сообщений раз в секунду только пока есть PENDING.
Один незавершённый вопрос на диалог. Повтор вопроса после ошибки — новое сообщение.
После перезапуска незавершённые сообщения получают FAILED. Обработка — до 120 секунд,
не более трёх раундов функций. Ошибка не содержит внутренних ответов Ollama/SQL.

`sources`: `{id,title,href,excerpt}`[] — реальные найденные материалы с текстом фрагмента и локальными ссылками.
`blocks`: дискриминированные карточки `{kind,title,product?,calculation?,application?,payment?,actionId?,action?,resultId?}`.
Виды: product, calculation, application, payment, action, result. Числа и карточки
формирует сервер по результатам доменных функций, не из свободного текста модели.
Параметры action: `{kind: draft|ticket, draft?: {productCode,amount,term,goal}, productName?, goalLabel?, subject?, text?}`.
Предложение хранится на сервере и связано с диалогом; клиент передаёт только actionId.
Повтор подтверждения использует сохранённый результат. Для восстановления после сбоя
доменная команда получает стабильный идентификатор, исключающий дубликат даже при
одновременных подтверждениях. HTTP-вызовов внутри транзакции нет.
Черновик использует тот же доменный сервис и проверки полномочий.
Никакой отправки заявки, согласий и подписания через ассистента нет.

Межзонные данные поступают через shared-интерфейсы Catalog, Origination, Servicing.
Пользовательский текст и найденные фрагменты считаются данными, а не инструкциями.
Модель не получает SQL, доступ к файлам или произвольным URL. Условия кредита берутся
из каталога при вызове; расчёт выполняет калькулятор Catalog.

Знания: подготовленные Markdown в `backend/internal/support/knowledge`; отдельная команда
`go run ./cmd/support-index`. BGE-M3 dense (1024), полнотекстовый поиск PostgreSQL,
объединение reciprocal rank fusion, максимум пять источников. Обновление индекса атомарное;
хеши и версия сохраняются, удалённые фрагменты удаляются. Нет личных данных и исходников.
Встроенные FAQ включаются при индексации. Все конфигурации запуска и ограничения — `deploy/SUPPORT_AI.md`.

Зона Support (`backend/internal/support`, разработчик A): частые вопросы и обращения клиента. Схема БД — `support`,
вопросы — seed-миграция `0002_seed.sql`.

Ответы на обращения пока никто не пишет: кто отвечает (сотрудник банка или только частые вопросы) — открытый вопрос
в `backend/TASKS.md`. Поэтому обращение остаётся в статусе `OPEN`, `reply` — `null`, уведомление `TICKET_REPLY`
не отправляется.

## API

### `GET /support/faq?step=APPLICATION`

Реализовано. Открыто без входа. Частые вопросы по шагу пути клиента: `PRODUCT`, `APPLICATION`, `DOCUMENTS`,
`STATUS`, `DECISION`. Без `step` — по всем шагам. Неизвестный шаг — `400 VALIDATION_ERROR`.

```json
[
  { "id": "f-4", "step": "APPLICATION", "question": "Нужно ли загружать документы или выписки?", "answer": "Нет. Данные о компании, руководителе, учредителях и оборотах банк берёт из ваших счетов и государственных реестров." }
]
```

Шаг `DOCUMENTS` — про документы к подписанию, которые банк формирует сам: загрузки документов в кабинете нет.

### `POST /support/tickets`

Реализовано. Новое обращение клиента (пользователь с компанией; сотрудник банка — `403`). Со страницы заявки фронт
передаёт `applicationId`; это может быть только заявка своей компании, иначе — `400 VALIDATION_ERROR` по полю
`applicationId` (о чужой заявке через поддержку ничего не узнать).

Запрос:
```json
{ "subject": "Устаревший фактический адрес", "text": "В заявке старый адрес склада, мы переехали", "applicationId": "a-1031" }
```
Ответ `201`:
```json
{ "id": "t-12", "status": "OPEN", "createdAt": "2026-10-20T11:00:00Z" }
```

`subject` — до 200 символов, `text` — до 4000. `POST /admin/seed/reset` удаляет обращения, частые вопросы остаются.

### `GET /support/tickets`

Реализовано. Обращения текущего пользователя (последние 100), недавно изменённые первыми. Обращения коллег из той же
компании не показываются: это переписка конкретного человека.

```json
[
  { "id": "t-12", "subject": "Устаревший фактический адрес", "text": "В заявке старый адрес склада, мы переехали", "status": "OPEN", "reply": null, "applicationId": "a-1031", "updatedAt": "2026-10-20T11:00:00Z" }
]
```
