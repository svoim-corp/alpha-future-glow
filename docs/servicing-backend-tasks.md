# Доработки Servicing: постановка для серверной реализации

Дата: 21.10.2026. Связанные документы: [текущее обслуживание кредитов](servicing.md), [договор и выдача](offer.md), [состояния заявки](application-states.md).

**Статус: реализовано на сервере 22.10.2026** — фактический контракт в [servicing.md](servicing.md). Документ сохранён как постановка; принятые решения — в разделе «Принятые решения» в конце. Клиент к новым запросам ещё не подключён.

## Исходное состояние

В коде уже есть `GET /loans`, `/loans/summary`, `/loans/{id}`, `/loans/schedule`, `/loans/schedule/upcoming`; кредит и аннуитетный график создаются при выдаче через `shared.Loans.Open`. Текущий контракт описан в `servicing.md` и продолжает действовать.

В `servicing.payments` хранятся плановые основной долг, проценты и итог; состояние — `PLANNED` или `PAID`. `OVERDUE` вычисляется при чтении. Сумм фактического частичного погашения и журнала банковских проводок нет. Остаток долга сейчас уменьшается только на основной долг полностью оплаченных строк. Операций списания, досрочного погашения и закрытия кредита нет. `GET /loans` возвращает не более 100 записей без пагинации.

Клиент уже показывает полный график, разделы оплаченных/просроченных платежей, CSV и существующие HTML-документы договора. После серверных доработок потребуется отдельное согласованное подключение новых полей и действий клиента.

## Общие требования и зависимости

- Все клиентские пути в примерах начинаются с `/api/v1`. Клиент работает только с кредитами своей компании; чужой и несуществующий кредит возвращают одинаковый `404 NOT_FOUND`. Права на списание проверяются отдельно от права чтения.
- Суммы API — целые рубли, положительные суммы команд — `> 0`; ставки — проценты годовых, сроки — месяцы. Вычисления выполнять без накопления ошибок двоичного `float`; точность внутренних начислений и момент округления согласовать до реализации.
- Даты — `YYYY-MM-DD`, моменты событий — ISO 8601 с часовым поясом. Текущее обслуживание использует UTC: сохранить это поведение до отдельного решения об операционном дне банка.
- Добавить финансовую `version` кредита и `scheduleVersion` графика в ответы деталей, расчётов и команд. `If-Match` новых финансовых команд относится к версии кредита, а не заявки. Менять финансовую версию при проводке, существенном начислении, изменении резервов/незавершённых операций и закрытии. Перерасчёт создаёт новую версию графика.
- Команды с побочным эффектом требуют `Idempotency-Key`. Повтор одинаковой команды возвращает тот же идентификатор операции; изменённое тело с тем же ключом отклоняется как `400 VALIDATION_ERROR`. Сохранённый результат той же команды нужно распознавать до повторной проверки уже изменившейся версии, после проверки полномочий и принадлежности компании. Повторный ответ `202` не означает текущий статус операции: его получают отдельным `GET`.
- Нужна защита от одновременных повторов, двойного списания и двойной проводки: уникальность бизнес-операции и внешней транзакции, блокировка/проверка версии в транзакции, сохранение отпечатка запроса. Существующее middleware идемпотентности кеширует ответ после выполнения, не сравнивает тело и не сериализует конкурентные запросы — для денежных команд его одного недостаточно.
- Внешнее списание и получение подтверждения реализуются через Integrations и HTTP к настроенному внешнему сервису/контейнеру моков. Servicing не вызывает внешний банк напрямую и не читает чужую схему БД. Связь зон — через небольшие контракты `shared`/события.
- Подтверждение банка, проводка, распределение суммы, версии, остатки и переход статуса должны давать согласованный результат. Нужен сохраняемый механизм повторной обработки внешних результатов после сбоя; одного события в памяти недостаточно.
- Ошибки — существующий формат `code`, `message`, `fields`, `traceId`: `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 INVALID_TRANSITION`, `412 VERSION_CONFLICT`, `422 BUSINESS_RULE`, `502 UPSTREAM_UNAVAILABLE`. Коды конкретных причин в `fields[].code` ниже тоже являются предложением. Сообщения для кредита не должны ошибочно говорить об изменении «заявки».

## 1. Фактические оплаты и частичное погашение

### Задача

Дать клиенту возможность отправить запрос на оплату с разрешённого счёта компании, получить результат и увидеть фактически учтённые суммы. Частичная оплата не должна помечать весь платёж выполненным. Сервер должен различать поручение на списание, подтверждение банка и распределение поступивших денег.

### Предлагаемые запросы

| Запрос | Назначение |
|---|---|
| `GET /loans/{loanId}/repayment-accounts` | Разрешённые счета компании для списания: `id`, `maskedNumber`, `currency`, доступность операции; доступный остаток — только если его действительно отдаёт источник |
| `POST /loans/{loanId}/repayments` | Создать запрос обычного погашения; `If-Match` + `Idempotency-Key` обязательны |
| `GET /loans/{loanId}/repayments/{repaymentId}` | Статус запроса и, после подтверждения, распределение фактической суммы |
| `GET /loans/{loanId}/repayments?page=1&size=20` | История фактических операций и их результатов в стандартной обёртке `items/page/size/total` |

Все пути в таблице — под `/api/v1`. `accountId` клиент получает из первого запроса; нельзя доверять переданному произвольному номеру счёта или признаку принадлежности компании.

Для этой версии контракта допустимы только рублёвые списания без неявной конвертации. При отсутствии достоверных данных о доступном остатке нельзя показывать выдуманный ноль; проверку возможности списания выполняет источник. История операций сортируется по `requestedAt DESC, id DESC`; `size` — 1–100, по умолчанию 20. Операция, не принадлежащая указанному кредиту/компании, возвращает `404`.

Пример команды:

```http
POST /api/v1/loans/l-55/repayments
If-Match: "7"
Idempotency-Key: <уникальный ключ команды>
Content-Type: application/json

{ "accountId": "acc-1", "amount": 20000 }
```

Пример ответа `202 Accepted`:

```json
{
  "id": "rp-501",
  "loanId": "l-55",
  "status": "PENDING",
  "requestedAmount": 20000,
  "postedAmount": null,
  "allocation": null,
  "requestedAt": "2026-10-21T10:00:00Z",
  "postedAt": null,
  "loanVersion": 8,
  "scheduleVersion": 1
}
```

Предлагаемые статусы операции: `PENDING`, `PROCESSING`, `SUCCEEDED`, `FAILED`. Таймаут внешнего сервиса не доказывает отказ списания: операция остаётся на сверке до достоверного результата. Клиент получает её состояние через `GET`, а не повторяет списание с новым ключом.

В ответе подтверждённой операции должны появиться `postedAmount`, `postedAt`, `externalTransactionId`, `allocation` с суммами `principal`, `interest`, `penalties`, `fees`, а также `unappliedAmount`, актуальные версии и `loanStatus`. Сумма распределения и нераспределённого остатка равна фактически поступившей сумме. Исходный счёт показывается маскированным; технические реквизиты не раскрываются без необходимости.

### Подтверждение со стороны банка

В Integrations нужен адаптер подтверждений списания: проверенный callback либо опрос статуса у источника. Для callback предлагается служебный `POST /api/v1/internal/integrations/repayment-events`; он не относится к клиентским маршрутам и не доступен по обычной клиентской сессии. Формат и аутентификацию окончательно определить по выбранному источнику.

Минимальный внутренний результат после проверки адаптером: идентификаторы события, запроса и внешней транзакции, результат, фактическая сумма, валюта и момент проведения. Корреляция с компанией/кредитом определяется сохранённой операцией, а не доверенными полями callback. Дубликат события не создаёт вторую проводку. Если операции поступают вне кабинета, нужен отдельный согласованный способ сопоставления с кредитом и сверки; подставлять случайный кредит нельзя.

### Изменения чтения

Сохранить значения `principal`, `interest`, `total` строки графика как плановые. Добавить устойчивый `id` строки, `paidPrincipal`, `paidInterest`, `remainingPrincipal`, `remainingInterest`, `remainingTotal`. Например:

```json
{
  "id": "sp-55-1",
  "date": "2026-11-20",
  "principal": 40458,
  "interest": 21500,
  "total": 61958,
  "paidPrincipal": 0,
  "paidInterest": 20000,
  "remainingPrincipal": 40458,
  "remainingInterest": 1500,
  "remainingTotal": 41958,
  "status": "PLANNED"
}
```

Это пример представления частичной оплаты, а не утверждение очередности списания долга и процентов. Правило распределения необходимо согласовать отдельно.

- Существующие статусы API v1 `PLANNED`, `PAID`, `OVERDUE` сохранить: частичная оплата видна по суммам; до полной оплаты строка остаётся плановой либо просроченной по дате. Новый статус частичной оплаты без обновления клиента не вводить.
- `balance` учитывать по всему фактически погашенному основному долгу, включая частичные оплаты.
- `nextPayment.amount` и `amount` в платёжном календаре должны отражать остаток к оплате, а не исходную сумму уже частично оплаченной строки. Просрочка по-прежнему отделена от ближайшего будущего платежа.
- Переплату нельзя терять или автоматически превращать в досрочное погашение без согласованного правила. Поведение излишка и максимально допустимая сумма обычной оплаты — открытое решение.
- Леджер операций и распределения хранится отдельно от плановых строк. История не должна исчезать при перерасчёте графика. Исправления/возвраты проводятся прослеживаемо, а не удалением записи об оплате; протокол возвратов согласовать с источником.

### Критерии готовности

Подтверждённая частичная оплата уменьшает только фактически погашенные компоненты. Ошибка и неподтверждённый запрос не уменьшают долг. Полностью погашенная строка становится `PAID`; непогашенный остаток после даты — `OVERDUE`. Повтор и конкурентный дубль не создают повторное списание/проводку. Сверка после перезапуска завершает зависшие операции без потери результата. Чтение списка, деталей, календаря и напоминаний согласовано с оставшейся суммой.

## 2. Досрочное погашение, перерасчёт и закрытие

### Задача

До подтверждения действия показать клиенту точную сумму и результат пересчёта. Применять новый график и закрывать кредит только после подтверждённой оплаты. Частичное и полное досрочное погашение должны быть отдельны от обычной оплаты.

### Предлагаемые запросы

| Запрос | Назначение |
|---|---|
| `POST /loans/{loanId}/early-repayment-quotes` | Сохранить ограниченный по времени расчёт: версия долга, сумма списания, распределение и новый график. Денег не списывает; повтор защищён `Idempotency-Key` |
| `POST /loans/{loanId}/early-repayments` | Подтвердить расчёт и запросить списание; обязательны `If-Match` и `Idempotency-Key` |
| `GET /loans/{loanId}/early-repayments/{requestId}` | Получить состояние выполнения и итоговые версии долга/графика |

Пример расчёта частичного погашения:

```http
POST /api/v1/loans/l-55/early-repayment-quotes
Idempotency-Key: <ключ расчёта>
Content-Type: application/json

{
  "type": "PARTIAL",
  "amount": 200000,
  "effectiveDate": "2026-10-21",
  "strategy": "REDUCE_TERM"
}
```

Здесь `amount` предлагается трактовать как общую сумму списания: сервер отдельно показывает долю погашения основного долга, процентов и начислений. Это значение и разрешённые стратегии (`REDUCE_TERM` / `REDUCE_PAYMENT`) нужно подтвердить продуктово до реализации.

Для полного погашения — `{ "type": "FULL", "effectiveDate": "2026-10-21" }`: сумму и распределение определяет сервер; клиент не складывает оставшиеся платежи самостоятельно. Поля `amount` и `strategy` для `FULL` не принимаются.

Ответ расчёта должен содержать:

- `quoteId`, `loanId`, `loanVersion`, `scheduleVersion`, `calculatedAt`, `effectiveDate`, `validUntil`;
- `type`, выбранную стратегию для частичного погашения, `amountToDebit` и `allocation`;
- `principalAfter`, `monthlyPaymentAfter`, `remainingPaymentsAfter`, `expectedCloseDate`;
- `schedulePreview` с датами и разбивкой будущих платежей; при полном погашении после даты исполнения будущих обязательств быть не должно;
- применённую версию правил начислений и предупреждения о суммах, которые могут измениться до даты исполнения. Для будущей даты это прогноз, а не гарантия фиксированной суммы списания.

Пример подтверждения:

```http
POST /api/v1/loans/l-55/early-repayments
If-Match: "8"
Idempotency-Key: <ключ подтверждения>
Content-Type: application/json

{ "quoteId": "eq-101", "accountId": "acc-1" }
```

Ответ — `202 Accepted` с `id`, `loanId`, `status`, `quoteId`, `requestedAt`; итог возвращается через `GET`. Срок действия расчёта, принадлежность счёта, полномочия, версия долга и наличие незавершённых операций проверяются повторно **до списания**. Устаревшая версия — `412`; истёкший или уже использованный расчёт — бизнес-ошибка без повторного списания. Расчёт одноразовый; повтор той же команды возвращает прежнюю операцию.

### Перерасчёт и закрытие

- Подтверждённое частичное досрочное погашение атомарно создаёт новую версию будущего графика. Фактические проводки, оплаченные суммы и прошедшие обязательства сохраняются; исходный график доступен для аудита.
- В текущем `payments` выдавать действующий график и связанную историю исполнения. Заменённые будущие строки хранить в архиве версий, не смешивать их с активными `PLANNED` и не вводить новый статус в старый DTO без обновления клиента. Отдельный пользовательский API просмотра архивных версий при необходимости согласовать дополнительно.
- Фактическая сумма исполнения должна соответствовать подтверждённым условиям. Изменение процентов, даты, долга, резервов или комиссий после расчёта требует нового расчёта/согласия либо заранее согласованного протокола будущего исполнения. Нельзя молча списать больше подтверждённой суммы.
- `SUCCEEDED` операции означает подтверждённые деньги и применённый результат в Servicing. Если деньги подтверждены, а применение не завершилось, повторная обработка завершает его; операция не должна ошибочно превращаться в отказ с возможностью повторного списания.
- Для обычного невозобновляемого кредита перевод `ACTIVE → CLOSED` выполнять после полного исполнения всех обязательств и завершения связанных денежных операций. Сохранить `closedAt` и причину. Остатки равны нулю, будущие строки не продолжают создавать платежи/напоминания. Оплаченные и отменённые перерасчётом обязательства различать: отменённое не помечать оплаченным фиктивными деньгами.
- То же правило закрытия применяется после последнего обычного платежа, а не только досрочной оплаты.
- Для возобновляемого лимита/овердрафта нулевой долг сам по себе не доказывает закрытие договора. Правило завершения лимита и источник этого решения нужно согласовать отдельно.
- Статус кредита принадлежит Servicing. Связанная заявка остаётся `ISSUED`: действующая машина Origination не разрешает `ISSUED → CLOSED`. Если потребуется менять её, это отдельное согласованное изменение Origination.

### Критерии готовности

Клиент видит результат до списания. После исполнения частичного погашения новая сумма основного долга и график сходятся с проводками; ранее оплаченные суммы не теряются. После полного погашения невозобновляемый кредит появляется в закрытых, ближайший платёж отсутствует, будущие напоминания прекращаются. Отказ, устаревший расчёт и повтор команды не меняют долг повторно.

## 3. Пени и полная задолженность

### Задача и запрос

Добавить `GET /api/v1/loans/{loanId}/debt` — актуальное обязательство на момент серверного расчёта с отдельной просрочкой. Не считать его суммой всех оставшихся платежей: будущие ещё не начисленные проценты не равны текущему долгу.

Пример предлагаемого ответа:

```json
{
  "loanId": "l-55",
  "loanVersion": 12,
  "scheduleVersion": 2,
  "asOf": "2026-10-21T10:00:00Z",
  "businessDate": "2026-10-21",
  "timeZone": "UTC",
  "principalOutstanding": 1030000,
  "interestOutstanding": 15000,
  "penaltiesOutstanding": 1200,
  "feesOutstanding": 0,
  "totalOutstanding": 1046200,
  "overdue": {
    "since": "2026-10-15",
    "days": 6,
    "principal": 30000,
    "interest": 5000,
    "penalties": 1200,
    "fees": 0,
    "total": 36200
  },
  "unappliedFunds": 0,
  "calculationPolicyVersion": "policy-1"
}
```

Правила ответа:

- `totalOutstanding` — сумма четырёх компонентов задолженности. `overdue.total` — просроченная часть этой суммы, её нельзя прибавлять второй раз. При отсутствии просрочки `since: null`, `days: 0`, суммы просрочки нулевые.
- `unappliedFunds` — отдельный учтённый остаток средств; клиент не вычитает его автоматически из долга. Способ зачёта определяется согласованными правилами сервера.
- Ноль пеней допустим, когда расчёт выполнен и начислений действительно нет. Неизвестные правила или недоступный обязательный источник не подменяются нулями; вернуть понятную ошибку и не выдавать расчёт за полный.
- Зафиксировать в серверной политике базу и ставку пеней, начало/конец начисления, календарную базу процентов, округление, отсрочки, предельные суммы, льготные периоды и порядок погашения. **Значения не утверждены этой постановкой.** Текущая месячная формула графика не определяет автоматически правила ежедневных процентов при досрочном погашении и пени.
- Просрочка пересчитывается на границе операционного дня с учётом частичных оплат. История начислений и применённая политика должны позволять воспроизвести сумму.
- `balance` существующего API сохраняет смысл остатка основного долга; полная задолженность возвращается отдельно. Расчёт полного досрочного погашения использует тот же источник долга и явно обозначенную дату исполнения.

### Критерии готовности

Компоненты и итог сходятся до рубля; частичная оплата корректно уменьшает соответствующий долг и базу последующих начислений. Нет двойного включения просрочки, процентов и пеней. При согласованной нулевой ставке начисление равно нулю; отсутствие правила не выглядит как отсутствие долга. Все суммы рассчитывает сервер.

## 4. Пагинация кредитов и полные сводки

### Задача

Получать все кредиты компании без ограничения «первые 100» и показывать показатели по всей компании, независимо от открытой страницы.

### Предлагаемый совместимый маршрут

```http
GET /api/v1/loans/page?page=1&size=1&status=ACTIVE
```

```json
{
  "items": [
    {
      "id": "l-55",
      "product": { "code": "WORKING", "name": "Оборотный кредит" },
      "amount": 1200000,
      "balance": 1200000,
      "rate": 21.5,
      "term": 24,
      "issuedAt": "2026-10-20",
      "nextPayment": { "date": "2026-11-20", "amount": 61958 },
      "status": "ACTIVE"
    }
  ],
  "page": 1,
  "size": 1,
  "total": 135
}
```

`items` содержит записи формата текущего списка кредитов с согласованными дополнениями. Для компактного примера запрошена страница из одной записи; обычный размер страницы — 20.

- `page` начинается с 1, `size` — 1–100, по умолчанию 20. `status` необязателен: `ACTIVE` или `CLOSED`; отсутствие — все кредиты компании. Неизвестные значения/некорректные числа — `400`.
- `total` — количество с учётом фильтра, до ограничения страницы. Страница за пределами результата — `items: []`, `total` сохраняется.
- Стабильная сортировка: `issuedAt DESC, id DESC`. Чужие данные не попадают в счётчики или страницы. Список и количество согласованы на снимке данных запроса.
- Статический маршрут `/loans/page` зарегистрировать до `/loans/:id`.
- Старый `GET /loans` пока сохранить как массив для действующего клиента. Не заменять его объектом пагинации без согласованного обновления клиента. Новый маршрут — предложенный путь миграции; изменение основного маршрута/версии API можно согласовать отдельно.

### Расширение `GET /loans/summary`

Сохранить `activeLoans` и `nextPayment`, добавить `closedLoans`, `totalLoans`, `totalPrincipalBalance` действующих кредитов и сводку просрочки `overdue: { loans, payments, amount }`. Показатели считаются по **всей компании**, не по открытой странице. Для `overdue.amount` явно закрепить смысл полной просроченной задолженности из задачи 3; до готовности этого расчёта не смешивать её с суммой только плановых долга и процентов.

`nextPayment` остаётся ближайшей будущей датой и суммой непогашенных остатков всех кредитов именно в эту дату; просроченные суммы идут отдельно. Если платежей впереди нет — `null`, даже когда есть просрочка.

### Критерии готовности

Компания со 135 кредитами получает все записи через страницы без потерь в неизменном наборе данных. При разных `size`, фильтрах и последней неполной странице `total` корректен. Значения сводки не меняются из-за переключения страницы. После подключения нового API клиент может убрать предупреждение о пределе 100.

## 5. Серверный PDF полного графика

### Запрос и содержание

```http
GET /api/v1/loans/l-55/schedule/document?format=pdf
Accept: application/pdf
```

Успех — `200`, бинарный PDF, `Content-Type: application/pdf`, `Content-Disposition: attachment` с безопасным именем файла, `Cache-Control: private, no-store`. Ошибки возвращаются обычным JSON с соответствующим HTTP-статусом; клиент не должен сохранять такой ответ как PDF.

Документ должен содержать:

- номер договора, название продукта, дату выдачи, сумму, срок, ставку, отсрочку, состояние кредита;
- момент формирования, операционную дату, версии кредита и графика;
- все строки графика: порядковый номер, дата, плановые основной долг/проценты/итог, фактически оплаченные и оставшиеся суммы, статус;
- понятные итоги плановых, оплаченных и оставшихся сумм; пояснение, что будущие проценты графика не равны текущей сумме полного досрочного погашения;
- отметку об изменённом графике после досрочного погашения и доступный контекст закрытого кредита. Отменённые будущие обязательства не выдаются за оплаченные.

Для отчёта нужен согласованный снимок данных. Если оплата идёт параллельно генерации, суммы, статусы и версии внутри PDF должны относиться к одному состоянию. PDF формируется на сервере из данных Servicing, не из присланного клиентом HTML/графика и не из данных старого договора, если график уже изменён.

### Критерии готовности

PDF доступен только компании-владельцу, открывается с русским текстом и корректными шрифтами, содержит весь длинный график с повторяющимися заголовками таблицы и нумерацией страниц. Числа совпадают с тем же снимком API. Выгрузка работает для действующего и закрытого кредита, после частичной оплаты и перерасчёта. Неизвестный формат — `400`, чужой кредит — `404`.

## Порядок реализации и подключение клиента

1. Согласовать перечисленные ниже финансовые правила; добавить версии, журнал операций, защиту денежных команд и интеграционный источник подтверждений.
2. Реализовать учёт оплат и остатки строк; затем расчёт долга/начислений и досрочное погашение с закрытием. Пагинацию можно делать независимо, PDF — после стабилизации формата графика.
3. Обновить OpenAPI, миграции и актуальное описание реализации в `servicing.md`. Этот документ оставить как постановку, отмечая принятые решения и завершённые части.
4. Согласованно подключить клиент: версии, состояния операций, остатки к оплате, полную задолженность, пагинацию, серверные сводки и PDF.
5. До обновления клиента не включать для него денежные сценарии: текущая таблица использует плановые `principal/interest/total`, а не новые `remaining*`. Добавление полей без изменения клиента само по себе не делает частичные оплаты корректно отображаемыми.

## Решения, которые нужно согласовать до реализации расчётов

- Кто и в каком окружении подтверждает реальное движение денег; разрешена ли клиенту команда списания, какой счёт и какие полномочия нужны; как обрабатываются таймауты, внешние платежи, возвраты и отмены.
- Очерёдность распределения платежа, действия с переплатой и правила частичной оплаты. Отдельно — можно ли обычным платежом оплачивать будущие строки заранее.
- Формула процентов при досрочной оплате, пени/комиссии, календарная база, округление и операционный день. В документе нет утверждённых тарифов или банковских нормативов.
- Даты и минимальные суммы досрочного погашения, допустимые стратегии, срок жизни расчёта, что означает `amount`, возможное предварительное уведомление банка.
- Условия закрытия невозобновляемого кредита и возобновляемого лимита/овердрафта, действия с незавершёнными операциями и нераспределёнными средствами.

Критерии готовности выше описывают ожидаемое поведение для будущей реализации. Они не означают выполненную проверку. В рамках подготовки постановки код, клиентские моки, API и БД не менялись; браузер, тесты и сборка не запускались.

## Принятые решения (22.10.2026)

Согласовано с пользователем для демо, реализовано как политика `policy-1` (подробно — [servicing.md](servicing.md)):

- Пени — 0,1% в день от просроченных основного долга и процентов, дневное начисление с округлением до рубля; комиссий нет.
- Проценты текущего периода — ежедневно по ставке / 365 на остаток на начало периода, не больше процентов строки графика.
  Проценты, оплаченные заранее сверх начисленного, при досрочном погашении засчитываются в основной долг.
- Порядок погашения: просроченные проценты → просроченный основной долг → пени → проценты ближайшей строки → её основной долг.
- Обычная оплата — не больше «просрочка + пени + ближайшая строка»; переплата отклоняется, будущие строки заранее не гасятся.
- Досрочное погашение — только сегодняшней датой и без неоплаченных строк с датой сегодня или раньше; `amount` — вся сумма
  списания, стратегии `REDUCE_TERM` / `REDUCE_PAYMENT`; расчёт одноразовый, действует 15 минут.
- Невозобновляемый кредит закрывается автоматически после полного погашения. Овердрафт при нулевом долге остаётся `ACTIVE`,
  клиент закрывает его командой `POST /loans/{id}/close`. Заявка остаётся `ISSUED`.
- Подтверждение списания — опрос АБС через Integrations (фоновый сверщик и опрос при чтении операции), без callback.
- Списание разрешено руководителю или представителю с действующей МЧД; одна незавершённая денежная операция на кредит.
- `/loans/page` разбирает `page`/`size` так же, как остальные списки API (некорректные значения — значения по умолчанию);
  `400` — только для неизвестного `status`.
- PDF — библиотека `go-pdf/fpdf` и встроенный шрифт DejaVu Sans Condensed.
