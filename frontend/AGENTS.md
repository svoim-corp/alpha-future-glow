# AGENTS.md — frontend «Умный кредитный кабинет»

Правила для любых агентов (Claude, Codex, Cursor и т. д.) и людей, которые пишут код в `frontend/`.
Дополняют корневой `../AGENTS.md` (контракт API, git, язык); при конфликте приоритет у этого файла. `CLAUDE.md` — симлинк на этот файл.

**Правила обязательны.** Код, который их нарушает, не считается готовым, даже если «работает».

Большая часть правил проверяется автоматически:

```bash
npm run check   # typecheck + eslint + steiger (FSD) + тесты
```

Задача не закрыта, пока `npm run check` не зелёный.

---

## 0. Главное за 30 секунд

1. **Архитектура — Feature-Sliced Design.** Импорты только сверху вниз: `app → pages → widgets → features → entities → shared`.
2. **Слайс снаружи — только через public API** (`@entities/application`), внутри — только относительные пути.
3. **Слайсы одного слоя друг друга не импортируют.**
4. **Серверные данные — только RTK Query** (`baseApi.injectEndpoints`). Клиентское состояние — `createSlice`.
5. **Любая новая функциональность и любой багфикс — вместе с тестами.** Без тестов задача не выполнена.
6. **Нельзя глушить проверки**: `eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `any`, `!`-assert, понижение порогов покрытия, отключение правил Steiger — запрещены без явного согласования с человеком. Если правило мешает — остановись и спроси.

## Порядок работы агента

1. **Перед изменением** определи слой и слайс по шпаргалке (раздел 2.5). Если код не ложится ни в один слой однозначно — спроси, не угадывай.
2. **Сначала тест, потом код** для багфиксов; для фич — тесты в том же изменении. Не сообщай «готово» без тестов.
3. **После изменения** запусти `npm run check`. Если что-то красное — чини причину. Никогда не:
   - добавляй `eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `any`, `!`;
   - отключай правила в `eslint.config.js` / `steiger.config.ts`;
   - понижай пороги покрытия в `vitest.config.ts`;
   - удаляй и не ослабляй существующие тесты, чтобы они прошли.

   Если правило мешает решить задачу — остановись и опиши проблему человеку.
4. **Контракт API** — `../API_SPEC.md`. Не придумывай поля и эндпоинты.
5. **Не трогай без запроса** инфраструктуру: `eslint.config.js`, `steiger.config.ts`, `vite.config.ts`, `vitest.config.ts`, `tsconfig*.json`, `test/setup.ts`, `Dockerfile`, `nginx.conf`.
6. Шаблон пустой: первый слайс в каждом слое задаёт стиль для остальных — делай его по этим правилам особенно аккуратно и с тестами по разделу 5.

## Команды

```bash
npm ci                 # установка зависимостей (строго по lock-файлу)
npm run dev            # dev-сервер :3000, /api проксируется на VITE_API_PROXY_TARGET (по умолчанию :8080)
npm run check          # typecheck + lint + lint:fsd + test — обязателен перед завершением

npm run test:watch     # тесты в watch-режиме
npm run test:coverage  # тесты с покрытием (пороги не понижать)

```

Весь проект (сервер, БД, моки, клиент за nginx) — через `../deploy` (`docker compose up --build`).

## 2. Feature-Sliced Design

### 2.1 Слои

| Слой | Что лежит | Пример в проекте |
|---|---|---|
| `app` | Инициализация: стор, роутер, провайдеры, глобальные стили, точка входа. Без бизнес-логики. | `app/model/store.ts`, `app/routes`, `app/entrypoint` |
| `pages` | Страница = маршрут. Компонует виджеты и фичи, своей логики почти нет. | `pages/home` |
| `widgets` | Самостоятельный крупный блок страницы, собранный из фич и сущностей. | (пока пусто; напр. `widgets/my-applications`) |
| `features` | Действие пользователя, дающее бизнес-ценность: «отправить заявку», «принять оффер», «отфильтровать». | (пока пусто; напр. `features/submit-application`) |
| `entities` | Бизнес-сущности: типы, API, отображение. Заявка, продукт, компания, кредит. | (пока пусто; напр. `entities/application`) |
| `shared` | Переиспользуемое без знания о домене: UI-кит, базовый API, конфиг, утилиты. | `shared/ui`, `shared/api` |

### 2.2 Правило импорта (проверяет ESLint)

Слой импортирует **только слои ниже себя**:

| Откуда ↓ / Куда → | app | pages | widgets | features | entities | shared |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| app | — | ✅ | ✅ | ✅ | ✅ | ✅ |
| pages | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ |
| widgets | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |
| features | ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |
| entities | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |
| shared | ❌ | ❌ | ❌ | ❌ | ❌ | (внутри — относительно) |

Диагональ ❌ — **слайсы одного слоя не импортируют друг друга.** Если фиче нужна другая фича — композиция поднимается на уровень выше (widget/page), а общее опускается вниз (entities/shared). Кросс-импорт сущностей через `@x` — только по согласованию.

### 2.3 Public API

- У каждого слайса есть `index.ts` — это его единственная точка входа снаружи.
- Снаружи импортируем **только** `@<layer>/<slice>`: `@entities/application`, `@features/filter-applications`.
  Глубокие пути (`@entities/application/model/types`) запрещены.
- Публичный API `shared` — по сегментам: `@shared/ui`, `@shared/api`, `@shared/config`, `@shared/lib/<модуль>` (`@shared/lib/format`, `@shared/lib/store`).
- **Внутри своего слайса — только относительные импорты.** Через собственный `index.ts` и через алиас своего слоя не импортировать (циклы).
- Выходить из слайса относительным путём (`../../entities/...`) запрещено.
- В `index.ts` — только явные реэкспорты: `export { X } from './ui/X'`, `export type { T } from './model/types'`. `export *` запрещён. Наружу отдаём минимум, который реально нужен потребителям.

### 2.4 Сегменты

Внутри слайса код делится по **назначению**:

| Сегмент | Что |
|---|---|
| `ui/` | компоненты, стили |
| `model/` | типы, слайсы Redux, селекторы, zod-схемы, бизнес-логика (чистые функции) |
| `api/` | эндпоинты RTK Query (`baseApi.injectEndpoints`), DTO |
| `lib/` | вспомогательный код, нужный только этому слайсу |
| `config/` | константы, флаги |

Запрещены сегменты «по типу»: `components`, `hooks`, `helpers`, `utils`, `types`, `store`, `providers`, `reducers`, `selectors`, `actions`, `constants` (большую часть ловит Steiger). Файлы прямо в корне слайса — только `index.ts`.

### 2.5 Куда положить новый код — шпаргалка

- **Новая сущность бэкенда** (продукт, компания, кредит) → `entities/<name>/`: `model/types.ts` (по `../API_SPEC.md`, раздел 5), `api/<name>Api.ts`, `ui/` для отображения (карточка, бейдж), `index.ts`.
- **Новое действие пользователя** (отправить заявку, загрузить выписку, принять оффер, ответить на запрос банка) → `features/<глагол>-<существительное>/`: `ui/` (кнопка/форма), `model/` (схема, логика), `api/` (мутация, если она — команда этой фичи).
- **Блок страницы, который собирает несколько фич/сущностей** → `widgets/<name>/`.
- **Новый маршрут** → `pages/<name>/` + запись в `app/routes/router.tsx` + путь в `shared/config/routes.ts`.
- **Новый клиентский слайс Redux** → `model/` своего слайса + регистрация в `app/model/store.ts` (`combineSlices`).
- **Кнопка, инпут, модалка без домена** → `shared/ui/<Component>/` + реэкспорт в `shared/ui/index.ts`.
- Слово из предметной области (заявка, кредит, скоринг) в `shared` — признак ошибки: это `entities`.

### 2.6 Именование

- Слайсы и папки — `kebab-case`. Фичи — `глагол-существительное`: `submit-application`, `filter-applications`.
- Компоненты — `PascalCase.tsx`, один компонент на файл. Остальное — `camelCase.ts`.
- Стили — `<Component>.module.scss` рядом с компонентом.
- Тест — рядом с тестируемым файлом: `<file>.test.ts(x)`.
- Экшены слайса — в прошедшем времени, как события: `statusChanged`, `filtersReset`.
- Селекторы — `selectXxx`, объявляются в поле `selectors` слайса.

## 3. Данные и состояние

- **Серверные данные — только RTK Query.** Эндпоинты — через `baseApi.injectEndpoints` в `api/` слайса. Ответы сервера не копировать в `createSlice`. Не вызывать `fetch` / `axios` напрямую.
- Инвалидация кэша — через `providesTags` / `invalidatesTags`. Новый тип тега добавить в `tagTypes` в `shared/api/baseApi.ts`.
- **Клиентское состояние** — `createSlice` в `model/`; селекторы — в поле `selectors`; регистрация — в `app/model/store.ts`.
- В Redux кладём только то, что нужно нескольким компонентам или переживает смену страницы. Локальное состояние компонента — `useState`.
- Хуки стора — **только** `useAppDispatch` / `useAppSelector` из `@shared/lib/store` (сырые `useDispatch`/`useSelector` запрещены линтером).
- **Бизнес-логика — в чистых функциях** в `model/` (например, `filterApplications(items, filters)`). Компонент только вызывает их. Это и проще тестировать.
- **Типы DTO — по контракту API** (`../API_SPEC.md`). Если фронту нужно поле, которого нет в контракте, — сначала меняется спецификация (с пометкой «Доп.», если это наше допущение), потом код. Не выдумывать поля.
- Деньги — целые рубли (`number`), сроки — месяцы, даты — ISO-строки. Форматирование — только через `@shared/lib/format`.

## 4. Компоненты, стиль, UX

- Компоненты — стрелочные функции, **только именованные экспорты** (`export default` запрещён в `src/`).
- Пропсы — `interface <Component>Props`. Без `React.FC`.
- Стили — SCSS Modules и CSS-переменные из `app/styles/index.scss`. Цвета и радиусы — только переменными. Inline-стили — только для действительно динамических значений.
- **Доступность обязательна:** семантические теги, `<label>` у каждого поля, `role="status"`/`role="alert"` для загрузки и ошибок, `aria-*` где нужно. Тесты опираются на роли — недоступный UI не протестировать.
- Каждый экран с загрузкой данных обрабатывает **четыре состояния**: загрузка, ошибка (с возможностью повторить), пусто, данные.
- Тексты интерфейса — на русском.
- Всё внутри продукта: никаких email, SMS, мессенджеров, звонков — уведомления только в кабинете (ТЗ, стр. 11).
- Код-стиль (табы, одинарные кавычки, `;`, порядок импортов) — не обсуждается, его чинит `npm run lint:fix`.

## 5. Тесты — обязательны

### 5.1 Правило

**Новая функциональность = код + тесты в одном изменении.** Багфикс начинается с теста, который воспроизводит баг и падает, затем исправление. Изменение без тестов не считается выполненным, даже если просили «просто добавить кнопку».

### 5.2 Что и как тестировать

| Что | Тип теста | Что проверить |
|---|---|---|
| `model/` — чистые функции, zod-схемы | unit | все ветки, граничные значения, невалидный ввод |
| `model/` — редьюсеры и селекторы | unit | каждый экшен, каждый селектор |
| `api/` — эндпоинты | через компонент/хук + MSW | успех, ошибка бэкенда (формат `ApiError`), пустой ответ |
| `shared/ui` | компонентный | поведение по пропсам, состояния (disabled, loading), a11y-атрибуты |
| `features/*/ui` | интеграционный (`renderWithProviders` + MSW) | действие пользователя → изменение стора и/или запрос к API → результат на экране |
| `widgets`, `pages` | сценарный | загрузка, ошибка + повтор, пусто, данные; ключевые взаимодействия |
| `app/routes` | маршрутный | адрес → нужная страница, 404 |

Образцы в коде: `shared/lib/format/money.test.ts` (unit), `shared/ui/Button/Button.test.tsx` (компонент), `app/routes/routes.test.tsx` (маршруты). Шаблоны для слайса и для компонента с API:

```ts
// model/slice.test.ts — редьюсер и селекторы, без рендера
it('меняет статус фильтра', () => {
	const state = slice.reducer(initialState, statusChanged('DRAFT'));
	expect(state.status).toBe('DRAFT');
});
```

```tsx
// ui/MyApplications.test.tsx — компонент + стор + сеть через MSW
import { apiUrl, server } from '@test/msw/server';
import { renderWithProviders } from '@test/render';
import { screen } from '@testing-library/react';
import { http, HttpResponse } from 'msw';

it('при ошибке показывает алерт и умеет перезапросить', async () => {
	server.use(http.get(apiUrl('/applications'), () => HttpResponse.json(
		{ code: 'UPSTREAM_UNAVAILABLE', message: 'Мок недоступен' },
		{ status: 502 },
	), { once: true }));
	const { user } = renderWithProviders(<MyApplications />);

	expect(await screen.findByRole('alert')).toBeInTheDocument();
	await user.click(screen.getByRole('button', { name: 'Повторить' }));
	expect(await screen.findAllByRole('listitem')).not.toHaveLength(0);
});
```

### 5.3 Как писать

- Рендер — `renderWithProviders` из `@test/render`: свежий стор, роутер, `user` (userEvent). `@test` разрешён только в `*.test.ts(x)`.
- Запросы к DOM — по приоритету: `getByRole` → `getByLabelText` → `getByText`. `data-testid` — крайний случай с комментарием почему.
- Взаимодействие — `user.click / type / selectOptions`, не `fireEvent`.
- **Сеть — только через MSW** (`test/msw/handlers.ts` — счастливый путь, переопределение — `server.use(...)` в тесте). Необработанный запрос роняет тест. Не мокать RTK Query, `fetch`, свои хуки и модули через `vi.mock` — мокаем только внешние границы (сеть, время, случайность).
- Фикстуры — в `test/fixtures/`, строго в формате API (тип из public API сущности).
- Стор в тестах — настоящий; начальное состояние — через `preloadedState`.
- Тестируем поведение, а не реализацию: что видит и делает пользователь, что попало в стор/ушло в API. Snapshot-тесты запрещены.
- Названия `describe`/`it` — на русском и описывают поведение: `it('при ошибке показывает алерт и умеет перезапросить')`.
- Тесты независимы: без общего изменяемого состояния и порядка выполнения.

### 5.4 Покрытие

Пороги в `vitest.config.ts`: lines/functions/statements ≥ 80 %, branches ≥ 70 %. **Понижать запрещено.** `npm run test:coverage` — перед сдачей.

### 5.5 E2E

Сквозной сценарий ТЗ (вход → заявка → решение → подписание → выдача) — отдельный e2e-набор (Playwright, TODO). Unit/интеграционные тесты его не заменяют.

## 7. Запрещено (сводно)

- Импорт вверх по слоям, между слайсами одного слоя, мимо public API, через `../../` между слайсами.
- `export default` в `src/`, `export *` в `index.ts`.
- `any`, `as unknown as`, `!`, `@ts-ignore`, `@ts-expect-error`, `eslint-disable` без согласования.
- `fetch`/`axios` напрямую, данные сервера в `createSlice`, сырые `useDispatch`/`useSelector`.
- Бизнес-логика в компонентах; доменные понятия в `shared`.
- Сегменты `components/ hooks/ utils/ helpers/ types/ store/ providers/`.
- Мерж без тестов; моки собственных модулей; snapshot-тесты; понижение порогов покрытия.
- Платные/закрытые зависимости и API; email/SMS/мессенджеры в продукте.
