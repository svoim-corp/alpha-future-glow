# Контекст проекта и состояние frontend

Срез по коду и проверкам от **21.10.2026** (после переноса дизайна на UI-kit). Это навигация по текущей реализации, а не замена спецификации. При изменении сценария обновляйте соответствующую строку статуса и оставшиеся задачи. «Есть в клиенте» означает наличие React-кода и демообработчиков; это не подтверждение готовности сервера или полного соответствия требованиям.

## Что за продукт

«Умный кредитный кабинет» — веб-кабинет для юридических лиц и ИП, уже обслуживающихся в банке. Он помогает выбрать финансирование, заполнить двухэтапную заявку, получить решение, принять условия, подписать договор и перейти к обслуживанию кредита. Внешние проверки и выдача моделируются; подключения к реальным банковским системам в проекте не предполагаются.

Две роли:

- `CLIENT` — представитель компании: выбирает продукт, задаёт параметры, даёт согласия, отвечает на вопросы банка, принимает оффер и подписывает документы.
- `BANK_OFFICER` — сотрудник банка: работает с очередью, изучает заявку и результаты проверок, запрашивает пояснения, принимает решение или предлагает другие условия.

Основной путь: вход → каталог → черновик → предварительное решение → полная заявка → отправка → проверки/скоринг → решение → оффер → подписание → моделируемая выдача. Запрос информации возвращает клиента к уточнениям; отказ и встречное предложение — отдельные исходы. Точная машина состояний — в разделе 2 [API_SPEC.md](../../docs/API_SPEC.md).

По уточнению от 21.10.2026 реквизиты компании, полномочия и обороты известны банку. Клиенту не нужно вводить их заново или загружать выписки: мастер уже работает по этой модели (профиль компании из данных банка, поручитель выбирается из руководителя и учредителей, выписки нет). **Исключение: ввод ИНН на этапе 1 временно сохранён по решению пользователя от 21.10.2026; исправление отложено до отдельной задачи.** Это ограничение текущей работы, а не новое требование продукта.

## Где менять frontend

Пути ниже — относительно `frontend/`.

- `src/pages/` — страницы маршрутов; `src/app/routes/` — роутер и layouts.
- `src/widgets/client-shell/` — общая оболочка клиента; `src/widgets/bank-header/` — шапка банка.
- `src/widgets/product-catalog/`, `application-wizard/`, `application-tracker/`, `contract-signing/` — основные блоки кредитного пути.
- `src/widgets/my-loans/`, `payment-calendar/`, `planner-board/`, `support-center/` — кредиты, календарь, планер, поддержка.
- `src/features/` — действия: `start-application`, `edit-draft-params`, `request-prelim-decision`, `fill-full-application`, `answer-info-request`, `decide-offer`, `sign-contract`, `make-decision` и другие.
- `src/entities/` — типы, API и представления сущностей. DTO ещё требуют сверки с обновлённым API.
- `src/shared/ui/index.ts` — React UI-kit: кнопки, поля, карточки, бейджи, плитки Metrics, таблицы, модальные окна, шаги, иконки и состояния запросов. Наличие `FileUpload` не означает, что загрузка нужна в актуальном клиентском сценарии.
- `src/shared/lib/theme` — хук темы (светлая/тёмная), общий для клиентской оболочки и шапки банка.
- `src/shared/api/baseApi.ts` — RTK Query, cookie-сессия, типы тегов; `src/app/model/` — стор.
- `src/app/mocks/handlers.ts`, `db.ts`, `fixtures/` — демо API в браузере.
- `test/msw/`, `test/fixtures/`, `test/render.tsx` — моки и инфраструктура тестов; сами тесты лежат рядом с кодом. Демо и тестовые фикстуры — отдельные копии.

Демо-скрипты, синтетические цифры, галерейная навигация и неработающие элементы макета не становятся требованиями к продукту автоматически. Проверки Chrome, описанные в документации макетов, относятся к HTML-прототипам, а не к текущему React-приложению.

## Как работать без сервера

Из `frontend/`: `npm ci`, затем `npm run dev:mock`. Клиент — `http://localhost:3000`. Учётки: `smirnov` / `demo123` (клиент), `ivanova` / `demo123` (банк).

MSW включается через `.env.mock` (`VITE_MOCK=true`). Данные изменяются в памяти вкладки и сбрасываются при перезагрузке; сессия хранится в `sessionStorage`. Для просмотра решения от другой роли используйте смену пользователя в той же вкладке: вкладки не разделяют демобазу. В обычном `npm run dev` запросы идут через Vite к серверу.

## Оставшиеся задачи

Это выявленные направления работ, а не утверждение, что весь объём нужно реализовать в ближайшей задаче.

1. Решить судьбу ввода ИНН на этапе 1: по контракту компания определяется при создании черновика, а эндпоинт `POST /applications/{id}/company` из нового контракта убран. Уточнить у бэкенда. **Пока ввод не менять.**
2. Сверить с реальным API типы и команды мастера, карточки заявки, подписания и банка: до сервера всё проверено только на моках.
3. Для планера отдельно определить объём расширения: редактирование, состояния, правила актуальности рекомендаций и уведомлений. Почтовые уведомления не реализовывать: текущий продукт использует только кабинет.
4. Почистить моки поддержки от вопросов про выписку из 1С, которой в продукте больше нет. Подбор в моке отвечает для овердрафта «Только для клиентов банка», хотя все пользователи уже клиенты банка: уточнить, нужна ли такая причина.
5. Исправить `npm run check`: ESLint падает на JS из `docs/designs/` и `docs/ui-kit/`. Добавить E2E для пути от входа до выдачи после готовности интеграции; Playwright-набора в репозитории нет.
6. По мере готовности сервера проверять сценарии через `deploy/`; не переносить серверную бизнес-логику в UI ради обхода отсутствующих эндпоинтов.
