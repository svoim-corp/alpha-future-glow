# AGENTS.md

Общие правила и навигация по монорепозиторию для AI-агентов и разработчиков.
Если в поддиректории есть свой `AGENTS.md` или `CLAUDE.md` (например, `backend/AGENTS.md`), он уточняет и дополняет этот файл; при конфликте приоритет у более вложенного.

## О проекте

**Умный кредитный кабинет** — кабинет для юрлиц и ИП: подбор кредитного продукта, двухэтапная заявка, проверка по внешним источникам (моки), скоринг, рабочее место сотрудника банка, оффер, подписание, выдача и обслуживание кредита.

Две роли: `CLIENT` (клиент-юрлицо) и `BANK_OFFICER` (сотрудник банка).

## Структура репозитория

| Путь | Что там | Стек |
|---|---|---|
| `API_SPEC.md` | Спецификация API, доменные зоны, машина состояний, модель данных. **Источник истины** для контракта между клиентом и сервером | — |
| `backend/` | Серверная часть: REST API `/api/v1`, бизнес-логика, работа с БД, интеграции с моками | Go |
| `frontend/` | Клиентская часть: кабинет клиента и рабочее место банка (`/bank/*`) | React |
| `deploy/` | `docker-compose` для запуска всего проекта целиком (сервер, клиент, БД, моки внешних сервисов) | Docker |

## Общие правила

### Контракт API

- `API_SPEC.md` — единый контракт. Меняешь API на сервере или ожидания на клиенте — сначала обнови спецификацию, затем код обеих сторон в одном изменении.
- Не придумывай эндпоинты, поля и коды ошибок, которых нет в спецификации. Если нужно новое — добавь в `API_SPEC.md` и пометь как «Доп.», если это наше допущение, а не требование ТЗ.
- Соблюдай соглашения из раздела 3: префикс `/api/v1`, деньги — целые рубли, ставки — проценты годовых, сроки — месяцы, даты — ISO 8601, единый формат ошибки, `If-Match` для версии заявки, `Idempotency-Key` для команд с побочным эффектом.

### Архитектура

- Сервер — **модульный монолит**: один пакет на доменную зону, общая БД, схема на зону.
- Зоны не лезут в данные друг друга напрямую. Статус заявки меняет только зона Origination (через её команды или доменные события).
- Внешние сервисы вызываются только из зоны Integrations и только через HTTP к контейнеру моков — никаких захардкоженных ответов в бизнес-логике.
- Клиент не вызывает моки напрямую — только API сервера.

### Изменения в коде

- Работай в рамках задачи: не рефакторь и не переформатируй несвязанный код.
- Следуй стилю окружающего кода: именование, структура, плотность комментариев.
- Изменение, затрагивающее и `backend/`, и `frontend/`, делай согласованно, чтобы проект собирался и работал после каждого коммита.
- Не добавляй зависимости без необходимости. Если добавляешь — объясни зачем.
- Не коммить секреты, токены, `.env` с реальными значениями. Демо-учётки и seed-данные — допустимо.

### Проверка

- Перед завершением задачи убедись, что затронутая часть собирается и тесты проходят (команды — в `AGENTS.md` или `CLAUDE.md`/README соответствующей директории).
- Для сквозных изменений проверь запуск через `deploy/`.
- Если что-то не удалось проверить — прямо скажи об этом.

### Git

- Ветка от `main`, понятные сообщения коммитов в повелительном наклонении («Добавить эндпоинт подбора продукта»).
- Один коммит — одно логическое изменение.

### Язык

- Код, идентификаторы, имена веток — на английском.
- Документация, тексты интерфейса и сообщения об ошибках для пользователя — на русском.
