# AGENTS.md

Общие правила и навигация по монорепозиторию для AI-агентов и разработчиков.
Если в поддиректории есть свой `AGENTS.md` или `CLAUDE.md` (например, `backend/AGENTS.md`), он уточняет и дополняет этот файл; при конфликте приоритет у более вложенного.

## О проекте

**Умный кредитный кабинет** — кабинет для юрлиц и ИП: подбор кредитного продукта, двухэтапная заявка, проверка по внешним источникам (моки), скоринг, рабочее место сотрудника банка, оффер, подписание, выдача и обслуживание кредита.

Две роли: `CLIENT` (клиент-юрлицо) и `BANK_OFFICER` (сотрудник банка).

## Структура репозитория

| Путь | Что там | Стек |
|---|---|---|
| `docs/API_SPEC.md`, `docs/API_SPEC_ADDITIONAL.md` | Частично устаревшие спецификации, исторический справочник; не эталон | — |
| `backend/` | Серверная часть: REST API `/api/v1`, бизнес-логика, работа с БД, интеграции с моками | Go |
| `frontend/` | Клиентская часть: кабинет клиента и рабочее место банка (`/bank/*`) | React |
| `deploy/` | `docker-compose` для запуска всего проекта целиком (сервер, клиент, БД, моки внешних сервисов) | Docker |

## Где что искать

- **Старые примеры API, доменные зоны и модель данных** → `docs/API_SPEC.md`; предложение планера → `docs/API_SPEC_ADDITIONAL.md`. Это справочники, а не эталон актуального поведения.
- **Фактические маршруты, DTO и правила** → код клиента и сервера, тесты и актуальная постановка задачи.
- **Как поднять проект локально** → README соответствующей части и `deploy/`.
- **Настраиваемая главная** → `docs/home-dashboard.md`; действующий API хранения → `docs/dashboard.md`. Каталог содержит 16 типов, начальная раскладка — восемь. Новые варианты добавляй согласованно в реестр, схему, начальные настройки, редактор и рендерер; не сохраняй финансовые данные в конфигурации.

- **Общий поиск клиента** → `docs/search.md`: Search объединяет провайдеры доменных зон; SQL остаётся в зоне владельца, клиентский API — в `entities/search`, поведение — в `features/global-search`.

### Актуальность документации

`docs/API_SPEC.md` и `docs/API_SPEC_ADDITIONAL.md` немного устарели и сохранены для справки. Проверяй, есть ли в `docs/` актуальное описание нужного функционала. Если в `docs/` нет других актуальных файлов с описанием нужного функционала, **не используй старые спецификации как эталон** и не восстанавливай по ним требования автоматически. Изучай текущую реализацию обеих сторон и тесты; недостающие продуктовые решения уточняй у пользователя. При расхождениях отделяй согласованное поведение от фактического состояния кода и ограничений демо. Описания модулей в `docs/` создаются при их реализации и доработках; заранее не заполняй их предполагаемым поведением.

## Общие правила

### Контракт API

- При изменении API сначала опиши согласованный контракт в актуальном файле модуля в `docs/`, затем согласованно обнови код клиента и сервера в том же изменении. Старые спецификации не имеют безусловного приоритета.
- Не придумывай неподтверждённые поля и эндпоинты. Новые решения фиксируй в актуальном описании модуля; явно отличай требование, допущение и уже реализованное поведение.
- Соблюдай общие соглашения API: префикс `/api/v1`, деньги — целые рубли, ставки — проценты годовых, сроки — месяцы, даты — ISO 8601, единый формат ошибки, `If-Match` для версии заявки, `Idempotency-Key` для команд с побочным эффектом.

### Архитектура

- Сервер — **модульный монолит**: один пакет на доменную зону, общая БД, схема на зону.
- Зоны не лезут в данные друг друга напрямую. Статус заявки меняет только зона Origination (через её команды или доменные события).
- Внешние сервисы вызываются только из зоны Integrations и только через HTTP к контейнеру моков — никаких захардкоженных ответов в бизнес-логике.
- Клиент не вызывает моки напрямую — только API сервера.

### Изменения в коде

- Работай в рамках задачи: не рефакторь и не переформатируй несвязанный код.
- Следуй стилю окружающего кода: именование, структура, плотность комментариев.
- Изменение, затрагивающее и `backend/`, и `frontend/`, делай согласованно, чтобы проект собирался и работал после каждого коммита.
- Не добавляй зависимости без необходимости. Если добавляешь — объясни зачем.
- Не коммить секреты, токены, `.env` с реальными значениями. Демо-учётки и seed-данные — допустимо.

### Проверка

- Перед завершением задачи убедись, что затронутая часть собирается и тесты проходят (команды — в `AGENTS.md` или `CLAUDE.md`/README соответствующей директории).
- Для сквозных изменений проверь запуск через `deploy/`.
- Если что-то не удалось проверить — прямо скажи об этом.

### Git

- Ветка от `main`, понятные сообщения коммитов в повелительном наклонении («Добавить эндпоинт подбора продукта»).
- Один коммит — одно логическое изменение.

### Язык

- Код, идентификаторы, имена веток — на английском.
- Документация, тексты интерфейса и сообщения об ошибках для пользователя — на русском.
