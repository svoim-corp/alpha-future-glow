# Дополнение к API_SPEC: Планер

Версия: 21.10.2026. **Все контракты ниже — предложение фронтенда по макетам** `frontend/docs/designs/planner.html`, `PLANNER.md`. В исходном ТЗ этого раздела нет, в основной спецификации (`API_SPEC.md`) их тоже нет — всё это **Доп.** (наше допущение). Бэкенд ещё не реализован; пока фронтенд работает на моках (MSW), которые повторяют этот контракт.

Соглашения те же, что в `API_SPEC.md` (раздел 3): префикс `/api/v1`, cookie-сессия, деньги — целые рубли, даты — ISO 8601, единый формат ошибки `{ code, message, fields?, traceId }`, `Idempotency-Key` для небезопасных повторов. Роль — `CLIENT`; данные видны только своей компании.

Новая доменная зона:

| Зона | За что отвечает | Владеет данными |
|---|---|---|
| **Planner** | Планы и идеи развития, по которым Catalog подбирает финансирование | `BusinessPlan`, `PlanRecommendation` |

Новый тег кэша на фронтенде: `Plan`.

> **Раздел «Документы» (библиотека файлов `/documents`, загрузка и прикрепление к заявке) удалён 21.10.2026.** По уточнению ТЗ все пользователи — действующие клиенты банка, данные для кредита у банка уже есть, и кабинет не просит клиента ничего загружать (см. `API_SPEC.md`, раздел «Пользователи — действующие клиенты банка»). Документы к подписанию (`GET /applications/{id}/contract`, `API_SPEC.md` 4.7) формирует банк, к библиотеке они не относятся.

## 1. Планер — `/planner`

Зона: Planner. Макет: `planner.html`, правила — `frontend/docs/designs/PLANNER.md`.

### Модель `BusinessPlan`

```json
{
  "id": "p-1",
  "title": "Ремонт помещения",
  "note": "Обновить торговый зал и зону выпечки",
  "goal": "REAL_ESTATE",
  "budgetRub": 2400000,
  "dateMode": "PERIOD",
  "startDate": "2027-06-01",
  "endDate": "2027-08-31",
  "state": "ACTIVE",
  "notifications": { "inApp": true, "email": false },
  "recommendation": null,
  "createdAt": "2026-10-20T09:00:00Z"
}
```

- `dateMode`: `DAY` (один день, `endDate` = `startDate`), `PERIOD`, `UNSCHEDULED` (даты `null`).
- `state`: `ACTIVE`, `PAUSED`, `DONE`, `ARCHIVED`. В подборе участвует только `ACTIVE`.
- `goal` — код цели из `GET /products/goals` (Catalog).
- Подбор начинается с `startDate` (для `UNSCHEDULED` — сразу после сохранения); по окончании периода автоматическое продвижение прекращается. День начала определяется часовым поясом компании.
- `recommendation` — подбор по плану или `null`, если подходящего продукта нет:
```json
{
  "productCode": "INVEST",
  "productName": "Инвестиционный кредит",
  "reason": "Цель и сумма укладываются в рамки продукта",
  "availableFrom": "2026-10-20"
}
```
Это предварительное соответствие по параметрам, не решение банка и не гарантия одобрения.

### `GET /plans?state=ACTIVE`
Список планов компании. `state` необязателен (по умолчанию — все, кроме `ARCHIVED`).

Ответ `200`:
```json
{
  "items": [ { "...": "BusinessPlan" } ],
  "summary": { "total": 3, "withPeriod": 2, "unscheduled": 1, "budgetRub": 4250000 }
}
```
`budgetRub` — сумма ориентиров, а не кредитных обязательств.

### `POST /plans`
Запрос:
```json
{
  "title": "Новая печь для пекарни",
  "note": "Увеличить выпуск хлеба",
  "goal": "EQUIPMENT",
  "budgetRub": 1200000,
  "dateMode": "UNSCHEDULED",
  "startDate": null,
  "endDate": null,
  "notifications": { "inApp": true, "email": false }
}
```
Ответ `201` — `BusinessPlan`. Ошибки `400 VALIDATION_ERROR`: бюджет должен быть положительным, `endDate` не раньше `startDate`, для `DAY`/`PERIOD` дата начала обязательна. `email: true` требует отдельного согласия (в этой версии почта не отправляется — только флаг).

### `PATCH /plans/{id}`
Частичное изменение (в том числе `state`). Тело — подмножество полей `POST /plans` плюс `state`. Ответ `200` — `BusinessPlan`.

### `DELETE /plans/{id}`
Ответ `204`.

### Уточнения сервера (Доп.)
- Доступ: план видит и меняет только его компания. Чужой план — `403 FORBIDDEN`, нет плана — `404 NOT_FOUND`. Сотруднику банка раздел недоступен (`403`).
- `id` плана — `p-N`.
- `GET /plans` отдаёт до 200 планов, новые первыми; `summary` считается по отданным планам. `state` — один из `ACTIVE`, `PAUSED`, `DONE`, `ARCHIVED`, иначе `400`.
- `POST`: `title` — 1–200 символов, `note` — до 2000, `goal` обязателен, `budgetRub` — целое > 0, даты — `YYYY-MM-DD`.
  Для `DAY` сервер сам ставит `endDate = startDate`; для `UNSCHEDULED` даты сбрасываются в `null`. Для `PERIOD` `endDate` обязателен.
- `PATCH`: передаются только меняемые поля, отсутствующее поле не меняется. Пустая строка в `note` очищает описание; даты сбрасываются переходом на `dateMode: UNSCHEDULED`. После слияния план проверяется по тем же правилам, что и `POST`.
- `recommendation` вычисляется при каждом чтении: `null`, если план не `ACTIVE`, период уже закончился или подходящего продукта нет.
  `availableFrom` — `startDate`, если он в будущем, иначе сегодня.
- «Сегодня» — по московскому времени (часовой пояс компании; все демо-компании в Москве).

### Связь с уведомлениями
Когда по плану появляется подходящий вариант, создаётся уведомление `GET /notifications` с типом `PLAN_MATCH` (новый тип к `INFO_REQUESTED`, `DECISION`, `PAYMENT_DUE`, `TICKET_REPLY`), ссылка — `/planner`. Не чаще одного раза на один и тот же вариант.
Сервер (Доп.): уведомление получает автор плана, если `notifications.inApp = true` и подбор уже начался (`availableFrom` не позже сегодня);
проверяется при создании и изменении плана и при чтении `GET /plans` и `GET /plans/recommendations`.

### Виджет главной `plan-recommendations`
`GET /plans/recommendations` — идеи и планы, по которым уже есть подходящий продукт.

Ответ `200`:
```json
[
  {
    "planId": "p-3",
    "planTitle": "Новая печь для пекарни",
    "budgetRub": 1200000,
    "productCode": "INVEST",
    "productName": "Инвестиционный кредит",
    "reason": "Сумма и цель укладываются в рамки продукта"
  }
]
```
Пустой массив — виджет не показывается.
